Agent Architecture · Module 1 · Topic 1.3

Compaction and context editing

Why every summary is a bet, what the field learned this year about when to place it, and what you must exempt from it.

Freshness-checked 2026-09-06 · builds on 0.1 to 0.4, 1.1, 1.2 · ~14 min read

1Why this exists

1.2 left a debt here on purpose. It taught that between two model calls the harness has exactly four moves, that compress is the only one that destroys information, and that the field now recommends it last. Then it named the thing every team builds first anyway, the summarizer that fires when the window is full, "the guillotine," and promised that 1.3 would open on what the guillotine actually cuts. 1.1 made an older promise: it called rot a function of what is in the window, not of room left, and said the mitigation would come here. This is here.

The pressure is simple to state. Real work outgrows the window. A single coding session on a hard task now runs to millions of tokens across more than a hundred turns; research agents make hundreds of tool calls per question. And by 1.1, the model degrades long before the wall, so something must shrink the window while the task is still running. The moment the harness shrinks it, someone is deciding, on behalf of a future window that does not exist yet, what that window will need. That decision is the whole topic.

Two concrete failures show what is at stake. In a Johns Hopkins and Apple study published in June, an agent hunting a rare fungus on BrowseComp verified four facts, then a fixed-interval summary fired mid-reasoning, wiped them, and the agent guessed the wrong mushroom. On another question the fixed clock fired four times and each summary re-seeded the same list of already-ruled-out rock stars, so the agent looped inside its own dead ends for a hundred turns. A single compaction placed at the right moment, after the lead had been corrected, got the answer. Same model, same summarizer prompt; the only variable was when. The second failure is quieter. Two papers this summer measured what happens to standing rules under compaction: a policy the agent obeys perfectly while it is visible gets summarized at the same rate as a tool log, loses its exact wording, and stops being enforceable. Across seven models, compaction took constraint violations from zero to thirty percent. Nothing in the trace looks wrong. The agent simply no longer knows the rule.

The field's response in 2026 was not a better summary prompt. It was to stop treating compaction as one operation and start treating it as three decisions, which is the model below.

2The mental model

Carry this out of the room A compaction is a bet, placed by something that cannot see the future, on what a future window will need. You cannot make the bet safe. You can only decide when it fires, what is exempt from it, and how you find out it lost.

Unpack the three decisions, because every card in the landscape is an answer to one of them.

When it fires. The bettor can be a byte counter, a rule the model checks against its own trajectory, or a policy trained into the weights. 1.2 called this the trigger locus. What 2026 added is evidence that timing dominates: in the study above, the fixed clock's summaries changed a correct answer to a wrong one 40 percent of the times they changed anything at all, and letting the model fire at closed units of work beat the clock on 11 of 12 benchmark cells while spending less. A summary at a task boundary is a bet with good information. A summary at 150,000 tokens is a bet placed blind.

What is exempt. A summary is not uniformly lossy. It keeps the plot and loses the props. Narrative progress survives well ("we investigated the auth flow and found the bug in token refresh"); four other classes do not, and they are exactly what the next step needs: exact identifiers (paths, IDs, numbers, the order number from 1.2's quiz), standing constraints (policies, safety rules, "never touch prod"), the decisions taken and their reasons, and what was ruled out (the dead ends, which if lost get re-run). The syllabus compresses this to decisions over details. The 2026 refinement is that some details are not details: a constraint that loses its wording loses its force, so it has to be exempted from the bet rather than trusted to it.

How you find out it lost. A bad compaction does not throw an error. It shows up three turns later as a re-read, a repeated search, a forgotten branch name, a violated policy. 1.2's fourth card, the log-is-truth-window-is-view design, is the strongest answer: if the evicted turns still exist somewhere with a path in the summary, a lost bet is a re-read instead of a loss. Short of that, you get validation (checking a summary against the trajectory it replaced) and instrumentation (compactions marked in the trace, so the operator can see that the drift began at one).

One more thing the 1.2 framing did not have room for. Compaction is what the field calls it when the model or harness summarizes. Context editing is the umbrella for the lighter cuts: clearing old tool results, offloading big payloads to files, dropping stale thinking. Those are compress too, but they are structural rather than semantic, and they are the reason the field says "prune before you summarize." The first card is that.

3The landscape

A landscape of: what the compactor knows at the moment it decides.
What varies: the information available to whoever places the bet. A byte count; the shape of the content; the state of the task; the type of each line; the outcomes of past bets. Five answers, ordered from least to most informed, and the cost of being informed rises with the order.
Reading the diagrams: the row of small blocks is the window (turns and tool results), the model box is the compactor, the block after it is what replaces the window. Gray is shared structure; teal is what this approach knows that the one above it did not; the amber dot marks where it breaks.

Threshold summarization Current

A byte counter fires a summarizer. The Claude API's server-side compaction (compact_20260112) defaults to 150,000 input tokens, allows nothing below 50,000, and is Anthropic's recommended strategy for long-running agentic work; Claude Code auto-compacts near the limit and exposes /compact; Deep Agents fires at 85 percent of the model's window; Google's ADK fires every N events with an overlap. Two flavors, and the June paper names how they fail in opposite directions: reactive (near the limit) waits until the window is already saturated with stale tokens that have been polluting generation for many steps; periodic (every k tokens) cuts indiscriminately, often mid-subgoal.

Wins: predictable, testable, no model judgment required, and shipped as one API parameter; sessions become effectively unbounded. Costs: blind to trajectory state. On 20 production configurations, Claude Code's /compact on Sonnet 4.6 kept 53 percent of safety rules after one round and 10 percent after five (the "compaction cliff"). Fixed-interval summaries were net positive on competition math, but 40 percent of the answer changes they caused were for the worse.

Done right: a long-lived multi-turn chat product where there is no task boundary to detect and the bloat is uniform, paired with a wrap-up budget (count compactions, ask the model to finish at N) so unbounded does not mean infinite. Also correct as the backstop underneath every other card; SelfCompact keeps a 30 percent-of-window forced trigger behind its rubric.

Clearing and offloading Current

Structural cuts that need no summary. Anthropic's context editing clears old tool results while keeping the fact that the call happened; Deep Agents writes any tool input or result over 20,000 tokens to a file and leaves the path plus a ten-line preview in the window; on current Claude models the model's own earlier thinking blocks are simply dropped rather than summarized. Both platforms leave the system prompt untouched. This is compress by shape: the harness knows that a 30k-token file read is re-fetchable and that a decision is not, and cuts only the first kind. Cursor, Aider, OpenHands, Gemini CLI, and Codex CLI all run some version of this before their summarizer.

Wins: nearly lossless when the payload can be re-fetched; deterministic; the 29 percent eval lift 1.2 cited came from clearing alone; and it delays the summary, often past the end of the task, which is the best compaction of all. Costs: cuts one shape of bloat only; reasoning, decisions, and conversation are untouched; clearing the one result the next step needed becomes a re-read, and clearing it without a path becomes a loss.

Done right: every coding and computer-use agent, as the first move, before any summarizer is configured. Deep Agents states the ordering plainly: summarize only when nothing is left to offload.

Model-timed compaction Ascendant

The model decides when. LangChain shipped a summarization tool in Deep Agents in April (on by default in the CLI, opt-in in the SDK) and reported agents conservative about firing it but well-timed when they do: task boundaries, right after extracting a result from a large read, right before a complex multi-step stretch. The June SelfCompact paper adds the piece that makes it reliable: a rubric the model answers against its own trajectory before every fire. Has the trajectory reached a closed unit? Can the essentials be stated as three to five citable facts? Has anything progressed since the last compaction? Am I stuck in a way a summary would mask? Fire only when all four pass. The ablation is the finding: tool alone is used unevenly across models (some fire reflexively, some never); rubric alone cannot act; together they add 5 to 9 points on agentic search at 30 to 70 percent lower cost, and the fires land well before the fixed threshold would have.

Wins: bets placed with information; verified facts crystallize before reasoning continues; the loop-escape effect, where one well-timed compaction clears a dead-end shortlist that a clock kept re-seeding. Costs: the model has to remember, and it forgets under pressure (1.2's card three, again); the rubric is task-specific; the same model is judge, summarizer, and subject; and each probe is a call, cheap only because the prefix is cached.

Done right: research and search agents with natural sub-question boundaries, and coding agents at a task switch: "the refactor is done, now the tests." SelfCompact's rubric refuses to fire when the trajectory's value is dispersed across many small negative results, which is exactly the case where a summary would erase what was learned.

Typed retention Emerging

Not everything is summarized at the same rate. The Governance Decay paper (June) pins constraints so they pass through the rewrite verbatim; the Compaction Cliff paper (August) goes further and classifies each line of an agent's knowledge base by type, then routes each type through its own retention policy: rules kept exact, logs compressed, topics too big to compact safely split with the in-scope rules replicated into each part. The production seed already exists in plain form. The Claude API's pause_after_compaction hands control back after the summary so the harness can re-insert recent messages verbatim; its instructions parameter replaces the default summarizer prompt entirely, and Anthropic's own guidance for Fable 5.1 is to tell the model what the summary must retain. Community /compact rubric skills (keep, compress, drop, pointers) are the same idea by hand.

Wins: the exemption list becomes architecture instead of hope. In the seven-model study, violation with a surviving constraint was zero and with a dropped one was 38 percent; pinning closed that gap. Costs: something has to classify each line, and a rule misread as a log is a log; per-type policies are more surface to maintain; soft organizational policies decayed 8.3 times more than hard ones, so the classifier must catch the sentence that does not look like a rule.

Done right: any agent under standing policy that arrived through the conversation or memory rather than the system prompt: a support agent with refund rules loaded per account, a clinical or financial assistant, an agent with a "never do X" list a user typed on turn two.

Trained self-summarization Emerging

The summary is learned, not prompted. Cursor's Composer (March) trains on rollouts that are chains of generations linked by the model's own summaries; the final reward is applied to every token in the chain, so summaries that carried the right information forward are upweighted and summaries that lost it are penalized. Cursor reports the error introduced by compaction cut in half at a fifth of the tokens of a tuned prompt baseline, which is the only number in this landscape about summary quality rather than summary timing. Cognition described the earlier, cheaper form in 2025: a smaller model fine-tuned to compress Devin's history down to key details, events, and decisions.

Wins: the summary is optimized for what continuations actually needed rather than for what a prompt author guessed; short by construction; improves with every training run. Costs: you need the weights and one task distribution; the preservation list is implicit in the reward, so you can measure it but not read it; a policy learned on coding does not transfer to your support agent; and the vendor owns it, so it improves on their schedule.

Done right: a vertically integrated product with one task shape and its own model, which is why this card is Cursor and Cognition and not the rest of us. For everyone else, the lesson it teaches is that the bet can be scored, which is what the next card up (typed retention) and 6.2's verifiers do without training.

Two things the cards share. First, they stack rather than compete: a serious 2026 harness runs clearing first, one of the two summarizers second, and typed retention around whichever summarizer it chose, with the threshold as a forced backstop behind all of it. Second, every one of them is still a bet. The recovery decision (log-is-truth, validation, trace markers) sits underneath the whole landscape, and 1.2 already gave you its cards.

4Choosing

When designing an agent, ask yourself these questions to decide how the window gets shrunk, who decides when, and what is exempt:

Question 1 is load-bearing because it turns the mental model into a deliverable. Every card is a bettor; none of them can be briefed without a list of what the stakes are. Teams that skip it end up with a summarizer prompt written by whoever was on call, and Anthropic's own docs now say the same thing from the other side: custom instructions replace the default entirely, so if you write them, say what must be retained. Questions 2 and 3 are the cheap wins (structural cuts and exemptions cost almost nothing and remove most of the risk), which is why they come before the interesting question 4. Question 5 exists so that you recognize the trained card as someone else's move.

5Seen in the wild

Amp, the coding agent from Sourcegraph, changed its answer to this topic twice in seven months, and both answers were right when made. That makes it a better anchor than any single system, because you get to watch the bettor change.

October 2025: "Handoff (No More Compaction)." Amp removed automatic compaction. The post's reasoning reads like this lesson's section 2: compaction is lossy, whether the summary contains what you think it should is up to the agent, and, the part nobody else had said out loud, compaction encourages long meandering threads, because you just compact when you run out and stack summary on summary. The replacement, Handoff, made the user the bettor: you state a goal for the next task, Amp extracts from the current thread what that goal needs, and you review the extraction before it seeds a fresh thread. In this lesson's terms: model-timed timing (the human picks the closed unit), typed retention by inspection (the human reads the exemption list), and recovery by construction (the old thread is still there on the server; a bad handoff is a re-read). They also shipped Fork (duplicate the window at a point) and thread references (pull from another thread on demand), which is 1.2's reversible-context card built for a person instead of a harness.

May 2026: "Amp, Rebuilt." Handoff is gone. The stated principle: build for what frontier models can do now, not for what once was, and "today's leading frontier models are great at handling compaction." Amp now compacts automatically when the window fills, and the post lists the babysitting it removed: watching context percentages, deciding when to hand off, extracting information in a panic. The human bettor was scaffolding that substituted for a model capability, and 0.4 told you what happens to that kind of scaffolding: "scaffolding that substitutes for model capability gets eaten by the next model release, while scaffolding that contains consequences survives every one of them." The server-side thread store survived; the handoff ritual did not.

Read the two posts against the three decisions and something sharper appears. Amp did not reverse on timing (it went from human-timed to threshold-timed, which by the June evidence is a step down in information) or on exemptions (the review step was the exemption list, and it is gone). It reversed because the recovery decision made the other two cheap: with every thread stored server-side and referenceable, a lost bet costs a re-read, so the value of a careful bettor fell below the value of not making the user be one. That is the 2026 pattern in one product: invest in recovery, and the timing and exemption decisions can be handed to whichever bettor is cheapest.

Aside: Claude Code is threshold summarization with a user-tunable exemption list (/compact <instructions>), and it is the system the August paper measured to get the 53-to-10-percent cliff. The cliff is not a Claude Code bug; it is what card one does to card four's content when card four is absent.

The misconception "Compaction loss is a summarizer-quality problem, so the fix is a better prompt or a smarter model." Half of the 2026 evidence says timing, not prose, decided the outcome: same summarizer, same model, and the fixed clock turned right answers wrong 40 percent of the times it changed one, while a rubric-timed fire with the identical summary prompt won. The other half says the loss is structural: a rule and a log compete for the same tokens, seven different models dropped rules at the same rate, and Cursor's trained summarizer, the best in the landscape, halved the error rather than removing it. The fix lives in the harness's three decisions, not in the summary's wording. Then hold the opposite error in the other hand: Amp did retire its human bettor because the models got better, and it was right to. What model progress buys is a cheaper bettor; what it does not buy is an exemption list or a recovery path, and those are yours to build.

6Check yourself

A support agent loads each customer's refund rules from a policy database into the conversation on turn two, then runs 150-turn sessions with server-side compaction at the default trigger. Compliance audits show rule violations clustering late in sessions. The engineer proposes lowering the trigger to 80k. Which card, and why is the proposal the wrong decision?

Typed retention. The rules arrived through the conversation, not the system prompt, so the API's protection of the system prompt does not cover them; they are summarized at the same rate as the chat log and lose the exact wording that makes them enforceable (the seven-model study: zero violations while the constraint survives, 38 percent once it is dropped). Lowering the trigger is a timing change; the failure is an exemption failure, and more frequent compactions would drop the rules sooner, not later. Fix: pin the policy lines, either by re-inserting them verbatim after the summary with pause_after_compaction or by giving the summarizer instructions that name them as must-retain, and instrument compactions in the trace so the next audit can see whether the drift begins at one.

A research agent runs 80-search hunts. It hits the window on hard questions. The engineer proposes summarizing every 40k tokens. You have seen the June evidence; what do you say, and what does the summarizer have to be told to keep?

Model-timed compaction with a threshold backstop, not a clock. Search has natural closed units (a sub-question resolved, a lead corrected), and the June cases show the fixed clock freezing a wrong lead into every summary or wiping four verified facts mid-derivation. Give the model a summarize tool and a rubric (closed unit, three to five citable facts, progress since last, not stuck), and keep the 40k as the forced fallback. The preservation list for this task has an item people miss: what was ruled out. Dead-end queries are dispersed low-value lines that a summarizer drops first, and dropping them is why the clock-driven run re-searched the same rock stars for a hundred turns. SelfCompact's rubric refuses to fire when the trajectory's value is that kind of dispersal; your instructions should say the same.

Your coding product runs on the Claude API with server-side compaction. A user reports that after a long session the agent "forgot which branch it was on" and started editing main. Give your first three hypotheses, in the order you would check them, and name the move each one implies.

All three are context hypotheses, which is the Module 1 bar. (1) An identifier was lost in the summary: branch names are props, and the default summarizer keeps the plot. Check the compaction block in the trace; fix with custom instructions that name identifiers and current git state as must-retain, or re-insert the last few turns verbatim after the pause. (2) The summary never happened: the docs note that with tools defined the model occasionally calls a tool during the summarization step and returns a compaction block with null content; the window then continues from nothing. Check for null; fix with an instruction that forbids tool calls in the summary. (3) The compaction fired too early because tool results were bloating the window: big file reads should have been cleared or offloaded first (card two), so the summarizer fires less often and later, and a task-switch fire would have had a clean unit to summarize. Only after these would you consider the model.

Done when Module 1's bar is "given any agent misbehavior, your first three hypotheses are all context hypotheses, and they are usually right." 1.3's contribution: when a system gets worse right after it got smaller, you reach for three questions in order, what did the summary miss, when did it fire, and could the loss be recovered, and you can name the card that answers each. 1.1 gave you the budget, 1.2 the four moves; 1.4 and 1.6 own select, 1.5 owns write, and 1.7 sends the bill for all of them, including the cache miss every compaction pays.
