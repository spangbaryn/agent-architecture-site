The agentic loop

Sketch any agent as loop plus tools plus context, and know which part you actually get to design.

Freshness-checked 2026-08-21 · landscape rebuilt 2026-08-22 with per-card diagrams · ~12 min read

1Why this exists

Single model calls plateau. Give a model a task with more than a few steps, or one whose shape depends on what it finds along the way, and a one-shot answer either guesses or gives up. The pressure that created agents was not "make the model smarter." It was "let the model look, act, and look again." That requires a loop, and a loop requires someone to decide what the model sees each time around.

2The mental model

Carry this out of the roomAn agent is a model running in a loop with tools. Everything in the system that is not the model is the harness, and the harness is what you get to design.

LangChain's formulation, March 2026: Agent = Model + Harness. If you are not the model, you are the harness.

The loop has four beats, each one a design decision. Gather context (what the model sees this turn, where most cost and most failures live). Act (parse the tool call, check it is allowed, run it). Verify (the test output, the stack trace, the ground truth; this is what separates an agent from a confident text generator). Repeat or stop (models are bad at this; they stop early and declare victory).

Nothing else is required. No planner, no reflection module, no memory subsystem. Add only what a specific failure forces you to add.

3The landscape

A landscape of: who builds the loop around the model, and what sits between the model and its tools?
What varies: how much the harness does between turns, from nothing (a bare while loop) to everything (a harness that rewrites itself). Five answers, ordered by how much harness each adds; the last one is the exception, where the harness is hidden rather than absent.
Reading the diagrams: gray is structure every approach shares; teal is the element that makes this approach different from the one above it; the amber dot marks where it breaks.

The minimal loop Current

Model, a few general tools, a while loop. The shape Anthropic describes in Building Effective Agents and the one Claude Code still has underneath.

Wins: nothing to maintain, improves for free as models do. Costs: no audit trail, no policy enforcement, unpredictable cost per task.

Done right: A coding agent pointed at a repo with a real test suite. The tests are the verifier, so the loop needs nothing added: run, read the failure, edit, run again. Claude Code is this at its core.

The scaffolded control plane Current

Bounded plan-execute-verify, a policy engine in front of tools, approval gates, checkpoints, tracing. The enterprise answer to "who let the model do that."

Wins: governable and auditable. Costs: every piece of scaffolding bets the model will not outgrow it, and that bet keeps losing.

Done right: An agent that executes production runbooks (restart a service, scale a cluster). A policy engine allowlists the commands, a human approves anything destructive, and the trace exists for the postmortem. The scaffolding is there because the actions are irreversible, not because the model is weak.

The outer loop Ascendant

A loop above the session that asks whether the agent is actually done and re-injects the goal into a fresh context, with state carried on the filesystem. Ronacher's "coming loop."

Wins: multi-session work, sidesteps context limits. Costs: needs a completion oracle.

Done right: A multi-day codebase migration: "make the suite pass on the new framework." Each session writes progress to a file, the outer loop restarts a fresh context from it, and "done?" is answered by the test suite, which is exactly the oracle this approach requires.

Auto-evolved harnesses Emerging

Harness components live as files and a closed observability loop edits them (arXiv 2604.25850; Weng's "harness engineering for self-improvement").

Wins: makes harness quality measurable. Costs: research stage, documented reward hacking.

Done right: A benchmark-driven harness lab: run a fixed eval suite, let an editor model propose edits to the system prompt and tool descriptions, keep only edits that raise the pass rate on a held-out set. Right when you have a trustworthy eval and the budget to run it hundreds of times; wrong anywhere else.

Agent frameworks as the loop Legacy

Import a framework, get a loop. The 2023 to 2024 default.

Wins: fast to a demo. Costs: the loop was the easy part, and the framework hid the part that mattered.

Done right: A Friday prototype to show a stakeholder that the idea works at all. Import the framework, wire three tools, demo Monday, then throw it away before anyone asks what the context looks like on turn five.

4Choosing

When designing an agent, ask yourself these questions to decide how much harness to build around the model:

The first question does most of the work. Without a mechanical verifier none of the loops can tell success from a confident stop, so the honest answer is to build the verifier or stay at a single call. After that the two questions are about consequences and duration: irreversible actions buy scaffolding, work that outlives a session buys an outer loop, and the minimal loop is what is left when neither applies.

5Seen in the wild

Claude Code. Small general tool set, standing context in CLAUDE.md, skills loading instructions on demand, subagents as a context pressure valve, permissions on irreversible actions, compaction for long runs. Almost every item on that list is a decision about what is in the context window at a given moment, which is why harness design and context engineering are two names for mostly the same discipline.

2026 work reports accuracy gaps of up to roughly six-fold across harnesses running the same model.

The misconceptionThat the loop is plumbing and the model does the real work. The six-fold spread says otherwise. But the opposite error is more seductive: assuming more harness is better harness. Structure that compensates for a weak model becomes a cage for a strong one. The skill is knowing which of the two mistakes you are currently making.

6Check yourself

Your agent stops after four turns and reports success on obviously incomplete work. Which beat is broken?

Verification, then stopping. The fix is not a better prompt, it is a mechanical completion check. Adding an outer loop first just makes the agent do wrong work more times.

An internal agent that files expense reports: minimal loop or scaffolded control plane?

Scaffolded, for one reason: the actions are irreversible and touch money. That justifies approval gates and an audit trail. It does not justify a planner or a state machine over the reasoning. Scaffolding earns its place by containing consequences, not by organizing cognition.

Someone says their framework "handles the loop for you." What is the follow-up question?

Show me exactly what goes into the context window on turn five. The loop is thirty lines. The context assembly is the product.
