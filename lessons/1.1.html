Agent Architecture · Module 1 · Topic 1.1

The attention budget

After this you will treat every token you put in front of a model as a purchase, and you will know the four ways the field pays for it.

Freshness-checked 2026-08-30 · builds on 0.1, 0.2, 0.3 · ~13 min read

1Why this exists

Module 0 kept arriving at the same wall from different directions. 0.1 ended with the note that harness design and context engineering are two names for the same discipline. 0.3 found that a tool surface is a context-budget decision wearing an API costume. Every open thread in the ledger pointed at the window. Module 1 is where we stop treating that as a coincidence and name it: nearly every architecture decision is a decision about what goes in the context window, when. This topic is the reason that sentence is true.

The engineering pressure is simple. Windows got big, and teams did the obvious thing: they put everything in. Full repos, full histories, every tool definition, every document. The results were worse, not better, and they were worse in a way that was hard to see, because the model kept producing fluent output while quietly getting less accurate. Chroma put numbers on this in July 2025 across 18 frontier models: performance falls as input grows, on tasks as simple as finding a sentence or repeating a list, and it falls non-uniformly, long before the window is full. Anthropic's September 2025 guide gave the field its vocabulary: the model has a finite attention budget, every token depletes it, and the job is to find the smallest set of high-signal tokens that produces the behavior you want.

So the problem is not "will it fit." The problem is that fitting is free and attention is not.

2The mental model

Carry this out of the room Every token in the window spends from a finite attention budget, so the question is never "does it fit" but "does this token pay for its seat."

Three things follow, and each one is a design rule.

Attention is not storage. A transformer relates every token to every other token. Add a token and you have not added a fact to a shelf; you have added a row and a column to a relationship matrix, and thinned the attention available to every existing pair. That is why degradation is gradual and why it starts immediately rather than at the limit. "Lost in the middle" (Liu et al., 2023) was the first sighting: accuracy on the same fact drops sharply when it sits in the middle of the input rather than at either end. Chroma's report generalized it: length hurts, but distractors that look like the answer hurt more, and a coherent, well-structured haystack hurts more than a shuffled one, because the model follows the narrative instead of finding the needle.

The budget is spent by everything, not just the task. System prompt, tool definitions, examples, conversation history, tool results, retrieved documents: they all draw from the same account. This is where 0.3's "errors are prompts" thread pays off. That lesson promised the idea would generalize, and here it is: every string the model sees is a prompt, and every prompt has a price. A verbose tool result and a bloated system prompt are the same mistake at different addresses.

Verbatim from 0.3, now with its second half: "A tool is two things at once: a contract with a deterministic system, and a prompt aimed at a non-deterministic one." In 1.1 the second half gets a budget line.

Altitude is the budget rule for instructions. Anthropic's framing for system prompts is a Goldilocks zone: hardcoded if-then rules are brittle and expensive (they buy behavior one case at a time), vague guidance is cheap and useless (it buys nothing). The right altitude is the smallest set of instructions that fully outlines expected behavior and leaves the model room to generalize. You already know this move from 0.2's autonomy dial. Altitude is the same dial applied to the prompt: how much of the decision do you write down versus delegate.

3The landscape

A landscape of: who decides what enters the window, and when?
What varies: the locus of the decision. Nobody decides (put it all in); the designer decides at build time; the harness decides at run time; the model decides at run time over a context it can program. Four answers, ordered from least to most runtime judgment.
Reading the diagrams: gray is shared structure; teal is what makes this approach different from the one above it; the amber dot marks where it breaks. The wide bracketed box is the context window; its fill shows how much of the budget the approach spends.

Stuff the window Contested

Put the whole corpus in and let the model sort it out. Champions: the long-context roadmaps of every lab (1M-token Claude and GPT-4.1, 2M Gemini, Llama 4's 10M claim), and any team whose first instinct on "the agent forgot" is "give it more." The bet is that the model's attention is uniform enough that curation is wasted effort.

Wins: zero infrastructure, no retrieval to get wrong, single-pass reasoning over everything at once. Costs: rot begins long before the limit and is invisible in the output; cost and latency scale with the whole corpus every call; coherent documents actively mislead the model into following their structure.

Done right: a single 60k-token contract review where nearly every clause bears on the question and there is no distractor material. When the task genuinely needs all the tokens and the total sits well inside the window's reliable zone, curation would only lose information.

Curate at build time Current

The designer decides, before any run, what the model should see: a system prompt at the right altitude, a minimal tool set with token-efficient descriptions, a few canonical examples rather than an exhaustive list of edge cases. Champion: Anthropic's context engineering guide, which is really this card written long. The bet is that a human who understands the task can pick a high-signal set once and reuse it.

Wins: cheapest per call; fully inspectable; the stable prefix caches (1.7 will price this). Costs: brittle when the task drifts from what the designer imagined; every new case tempts another rule, and the prompt slides down the altitude scale into if-then rot.

Done right: a support agent for one product with a known policy surface. The designer knows the fifty things that matter, writes them at policy altitude ("refunds within 30 days, escalate anything involving a chargeback"), and the model handles phrasing. The task is bounded, so build-time judgment is enough.

Budgeted retrieval at run time Current

The harness decides per step. Identifiers stay in context (paths, IDs, queries); the payload is fetched through a tool when needed, and only a bounded slice of it enters the window. This is 0.3's "signal, not payload" rule promoted to the whole architecture, and it is the mid-2026 production default for coding agents (grep and file reads over embedded snapshots) and the hybrid "retrieve a bounded set, then reason over it" shape most RAG products converged on. Champions: Anthropic, Manus, every serious coding agent.

Wins: spends budget on what this step needs; the window stays inside its reliable range for arbitrarily large corpora; the model can course-correct by fetching more. Costs: needs a locator that works (an index, a naming scheme, a grep-able repo); each fetch is latency; the model can miss what it never thinks to ask for. 1.4 owns the locator question.

Done right: a coding agent on a 400k-line repo. It reads the file tree (identifiers, cheap), greps for the symbol, opens two files, and never sees the other 398k lines. The verifier (tests) tells it when it fetched the wrong thing, so misses are recoverable.

Context as an environment the model programs Emerging

The model decides, over a context it never fully reads. Recursive Language Models (MIT, Zhang, Kraska and Khattab, Dec 2025, revised May 2026) put the entire prompt in a variable inside a Python REPL. The model inspects it with code, slices it, and calls fresh copies of itself on the slices, then assembles the answers. The window holds the program and the returns, never the corpus. On their long-context benchmarks an RLM built on GPT-5-mini beat plain GPT-5, and RLMs on GPT-5 beat compaction by a median of 26% while handling inputs two orders of magnitude past the window. Prime Intellect has called it the paradigm of 2026; the field has not decided yet.

Wins: effectively unbounded input; degradation stops being a function of total size; no designer or index needed up front. Costs: many sub-calls, so latency and cost are variable; a reproduction (Wang, Mar 2026) found deeper recursion makes models overthink and score worse; it is research infrastructure, not a product surface, as of this month.

Done right: an aggregation task over ten million tokens of support transcripts ("how many tickets in Q2 mention billing and were unresolved") where the answer requires touching nearly every record and no index exists. Neither stuffing nor retrieval can do this; recursion over slices can.

4Choosing

When designing an agent, ask yourself these questions to decide how the task's information gets into the window:

The load-bearing question is the second one on the left: can you know at build time what the model will need? If yes, you are in the cheap, cacheable, inspectable world and you should stay there as long as the task lets you. If no, you need runtime judgment, and the only question left is whether the harness has a locator good enough to exercise it. The "not yet" leaf is the one people skip: an agent with retrieval but no reliable way to find things is a stuff-the-window agent with extra steps.

5Seen in the wild

Cursor is a useful anchor because it exposes all three production cards in one product you have touched, and because it lets the user see the budget being spent.

Build-time curation is the rules layer: .cursor/rules files with scoping (always-on, or auto-attached by file glob). A rule file is a designer's decision about what every run in that part of the repo should see, made once. Notice the altitude problem in the wild: rules files that grow into fifty if-then lines are the brittle end of the dial, and good ones read like policy.

Budgeted retrieval is everything else: the codebase index (embeddings over the repo, one retrieval signal among several), plus the agent's own grep and file reads. Identifiers stay in context; payload comes in per step. The @file mention is the user manually overriding the locator, which is exactly the "not yet" leaf handled by a human: when the index cannot find it, you point.

Stuffing is the failure the product design is built to prevent, and you can watch it happen anyway. Drag a whole directory into a chat, or let a session run to the context limit, and the agent starts re-implementing things it already wrote and losing the goal. That is not a model getting dumber. It is the rot curve, and the product's compaction (1.3) is the mitigation.

One more sighting, because it is fresh and it is not a coding tool. A May 2026 paper tested AI-control monitors, a model reading an agent's transcript to catch a covert dangerous action. With Claude Opus 4.6 as the monitor, recall fell from 98.6% to 88% as transcripts approached 800k tokens. The same rot curve, in a safety system, on a frontier model, this year. Their partial fix was periodic reminders of the instructions throughout the transcript, which is 1.5's recitation pattern arriving early. Hold that thought; it is a debt this lesson will pay there.

The misconception "Million-token windows make context engineering obsolete." Wrong for two reasons stacked on each other. First, rot is a function of what is in the window, not how much room is left: Chroma measured degradation at fractions of the limit, distractors hurt more than length, and coherent input hurts more than shuffled. A bigger window moves the wall; it does not remove the slope. Second, look at what actually scales: Recursive Language Models process inputs a hundred times larger than the window, and they do it by keeping the corpus out of the window. The frontier answer to "how do I handle more context" is "read less of it at a time." Long windows are a capability. Attention budgeting is the discipline that decides whether the capability helps.

6Check yourself

You are building an agent that answers questions over a company's 2,000-page internal wiki. Your engineer says "the model has a 1M window, just load the whole thing." Which card, and what do you say?

Budgeted retrieval. The wiki is far bigger than any window's reliable zone, most questions touch a handful of pages, and a wiki is full of distractors that look like the answer (three pages on "expense policy" from different years). Loading it all is the stuff-the-window card in the exact conditions Chroma showed it failing: long, coherent, and full of near-misses. What you say: "It fits, but it will not pay for its seat. We need a locator: search over titles and sections, page IDs in context, load the two pages that matter." If the engineer pushes back with "but retrieval misses things," the honest answer is yes, so we build a verifier (cite the page, let the user check) rather than trade a visible miss for an invisible rot.

Your support agent's system prompt has grown to 40 rules over six months, and it still gets edge cases wrong. A teammate proposes adding rules 41 through 55. What is happening, and what is the alternative?

The prompt has slid down the altitude scale. Each rule was a build-time fix for one run-time surprise, and the accumulated rules now spend budget on cases that rarely occur while crowding the ones that do. This is curate-at-build-time hitting its failure point: the designer's judgment froze, and the task kept moving. Two alternatives: rewrite at policy altitude (ten principles, not fifty cases), or admit that this part of the task needs run-time judgment and move the case-specific material into something retrieved when relevant (1.6 will call this progressive disclosure). Adding rules 41 to 55 is the one option that makes both problems worse.

A product needs "count every customer email from Q2 that mentions a competitor by name." Ten million tokens of email, no index, answer due tonight. Which card?

This is the rare case where the first question in the tree is yes: the task needs nearly every token (you cannot count what you do not read). The whole input is nowhere near a reliable window, so stuffing is out. Retrieval fails because there is no locator and you are aggregating, not looking something up. That leaves the emerging card: treat the corpus as an environment, slice it, run sub-calls on slices, sum the counts. If you cannot stand up an RLM tonight, the pragmatic equivalent is a fixed-workflow fan-out from 0.2 (chunk, classify each chunk in a fresh context, aggregate), which is the same idea with the recursion written by hand. Either way, the corpus never enters one window.

Done when Module 1's bar is "given any agent misbehavior, your first three hypotheses are all context hypotheses, and they are usually right." This topic gives you the first hypothesis: the window is spending attention on tokens that are not paying for their seat. You should be able to look at any agent, name which of the four cards it is running, and say whether its budget is being spent by a designer, a harness, a model, or nobody. 1.2 will give you the vocabulary for the other hypotheses (the four operations and the four failure modes), and 1.3 through 1.7 supply the specific mechanisms.
