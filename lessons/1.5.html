Agent Architecture · Module 1 · Topic 1.5

Structured note-taking and recitation

Know who the agent is writing for when it writes something down, and design the note for that reader's distance rather than for the model that is writing it.

Freshness-checked 2026-09-11 · builds on 0.1 to 1.4 · ~13 min read

1Why this exists

Two failures, one cause. The first is drift. A typical Manus task runs about 50 tool calls, and somewhere around call 40 the agent forgets what call 1 was for. Nothing was compacted; the goal is still in the window. It is just far from the end, in the region 1.1 taught you to distrust, and the model is steering by whatever arrived most recently. The second is the cold start. Anthropic's first long-running harness watched Opus 4.5 try to one-shot a whole web app, run out of context mid-feature, and hand the next window a half-built thing with no explanation; later sessions would look around, see progress, and declare the project finished. Their write-up says it plainly: compaction "isn't sufficient."

You already own the pieces. 1.1 gave you the budget: "every token in the window spends from a finite attention budget, so the question is never 'does it fit' but 'does this token pay for its seat.'" 1.3 gave you the loss: "a compaction is a bet, placed by something that cannot see the future, on what a future window will need." What neither lesson told you is who should write down what that future needs, and when. That is this topic. The fix for drift and the fix for cold starts turn out to be the same object at two distances: a note the agent leaves for a reader who does not yet exist.

2The mental model

Carry this out of the room A note is a message from the agent to a later, poorer-informed version of itself; how far away that reader is decides what the note carries and how often it gets rewritten.

Three readers, three distances. The next step has the whole transcript but attends unevenly to it, so the note's job is placement: put the goal where attention is highest, which means the end. That is recitation: rewriting the plan into the recent tail of the window, every step, so the global objective is always the newest thing the model sees. Manus's todo.md is the canonical form. The next window has a summary of the transcript, and 1.3 told you what summaries drop: identifiers, standing constraints, decisions with reasons, what was ruled out. The note's job here is survival, so it lives outside the window, as a file, and it is written in the shape of the preservation list. 1.3 promised you would see that list again; this is where it lives when it is kept live instead of reconstructed at compaction time. The next session, or another agent, has nothing. The note's job is orientation: what exists, what is done, what is next, how to run it. Anthropic's claude-progress.txt plus a feature list plus a git log is the canonical form.

Distance sets the form (a rewritten tail, a file, a schema), the cadence (every step, at boundaries, once), and the bill. The same note written at the wrong distance is either wasted or lost. 1.2 asked you, without naming it, what to do about an order number that was said at turn 3 and gone by turn 30. That was a note question: who writes it down, and for which reader.

What varies: the writer (the model into its own transcript, the harness, the model into a file, a separate planner, the environment itself) and the reader's distance (the next step, the next window, the next session, another agent). Recitation in the transcript Legacy

The model maintains a plan (a todo list, a goal statement) and rewrites the whole thing into the end of its own transcript at every step, so the objective sits in the recency zone no matter how long the run gets. Manus (Jul 2025) named the pattern and the reason: "it's using natural language to bias its own focus toward the task objective." Claude Code's original TodoWrite and Deep Agents' write_todos are the same move as a tool call. The badge moved this year. Manus found roughly a third of all executor actions were spent updating the list rather than doing the task and moved planning out of the executor (per Lance Martin's notes on Peak Ji's Oct 2025 webinar). Claude Code's docs now say newer models "track multi-step work without a written todo list" and ship the task tools off by default for them. Recency was doing work that the models increasingly do on their own: 0.4's rule, in note form.

Wins: no infrastructure; the note carries what the model learned this run, not only what it was told; visible in the transcript, so a human can read the plan. Costs: every rewrite is an action and an append, so it spends both the action budget and the cache (1.7 will price this); the list is in the window and dies with it; a model that is already tracking state is being taxed for bookkeeping.

Done right: a mid-tier or open-weight model on a long tool loop where the observed failure is drift, and no session boundary is expected. The list is the cheapest fix for that specific failure, and you measure its action share to know when to stop.

Harness-injected reminders Current

The model writes nothing. The harness periodically re-inserts a fixed note (the task, the rules, the classification question) into the transcript, so recency is exploited without spending model actions on it. Claude Code's system-reminder blocks are this. The strongest recent evidence is from monitoring, not coding: in Classifier Context Rot (May 2026), Opus 4.6 with thinking caught an obvious dangerous action 99.7% of the time in a 100k transcript and 69% of the time when the same action was buried in 800k, and inserting periodic reminders of the task into the transcript recovered a significant part of the loss. Frontier models still rot; the reminder still pays.

Wins: deterministic, free of model actions, tunable per harness; the cadence is a dial you own. Costs: the note is static, so it recites the goal and the rules but cannot carry what the model has learned or decided this run; each insertion is an append with a cache cost; over-reminding is its own distraction.

Done right: any long-transcript classifier or monitor, and any agent whose standing constraints (safety rules, output schema, scope) are what it forgets. Governance Decay (1.3) showed soft constraints decay fastest; a reminder is the cheapest re-pin.

Structured state file Current

The model writes its working state to a file with a schema, outside the window, and the next window (or the next session) reads it back before doing anything. Anthropic's long-running harness (Nov 2025) is the reference: an initializer writes feature_list.json (over 200 features for a claude.ai clone, all marked failing), claude-progress.txt, init.sh, and a first commit; every later session starts with pwd, reads the progress file and the git log, picks one feature, and ends with a commit and a progress update. Two details are the whole design. Coding agents may edit the feature list only by flipping a passes field, under "strongly-worded instructions"; and the list is JSON because the model was "less likely to inappropriately change or overwrite JSON files compared to Markdown." The schema is the constraint. Claude Code's Tasks (on disk in ~/.claude/tasks, with dependencies, surviving compaction) are the productized version.

Wins: survives compaction, resets, and sessions; human-editable and diffable; git gives it a recovery path (1.3's third decision) for free; a schema turns "write good notes" into "fill these fields." Costs: what the writer omits is gone, and the writer cannot see the reader; a stale or optimistic entry (a feature marked passing without a test) misleads every later session; someone has to design the fields.

Done right: any task that outlives one window: overnight builds, multi-day research, anything with a human away from the keyboard. This tutor is one: the lesson ledger and the profile are the state file, and every run opens by reading them.

Planner-owned plan object Ascendant

A separate context writes the plan and the executor only reads it. Manus's fix for the one-third problem was exactly this: a planner sub-agent decomposes the task and returns a structured plan, the executor acts, and per Phil Schmid's account the plan is injected only when needed rather than rewritten every turn. Anthropic's March 2026 harness added a planner that expands a one-to-four-sentence prompt into a full spec (16 features across ten sprints for a retro game maker) and keeps it at the level of what and why, because a detailed plan that is wrong "would cascade into the downstream implementation." The executor is never the bookkeeper.

Wins: the executor's actions all advance the task; the plan is written once, in a context with nothing else in it; the plan's schema is enforced at the seam (Manus uses constrained decoding on sub-agent output). Costs: you are now multi-agent, with Module 4's bill and its crux, context sharing between planner and executor; a plan that does not receive results back drifts from reality; a planner that over-specifies poisons the build.

Done right: a general agent on 50-call tasks where the plan is large and the executor is spending measurable actions on maintaining it; the planner is a tool call the executor makes (Manus) or a first phase (Anthropic), not a peer that chats.

Environment-written notes: the failure trace Contested

The note nobody chose to write. A failed tool call, a stack trace, a wrong answer: the environment wrote it into the transcript and the question is whether to keep it. Manus's position, verbatim: "Leave the wrong turns in." Keep the failed action and its observation, because that is the evidence that updates the model's beliefs and stops the repeat. The syllabus calls this learning from failures mid-task, and SelfCompact's rubric (1.3) encoded the same instinct by refusing to compact a trajectory whose value was dispersed across dead-end queries. The counter-signal arrived in May 2026. Why Retrying Fails models the retry-with-history pattern and fits it to real SWE-bench Verified retries: an independent-attempts model overestimated pass@3 by 17.4 points (98.6% vs 81.2%), and the fit implied a per-step error rate about 7x higher inside a contaminated retry than on a clean one, with a proof that clearing context before a retry strictly reduces attempts needed. It is a model fit, not an ablation, but it names something every Claude Code user has watched: the agent that "repeatedly referenced the same bad endpoint in future attempts because it had learned from its own mistake."

Wins: free, and it is the only evidence the model has that a path is closed; a trace read once prevents the repeat. Costs: a whole failed attempt in the window is not a lesson, it is a wrong prior with momentum; the model defends its earlier reasoning instead of abandoning it; the contamination compounds across retries.

Done right: keep the failure, drop the attempt. The error signature, what was tried, and why it failed go into the ruled-out section of the state file (1.3's fourth preservation class); the failed diff and the reasoning that defended it get cleared before the retry. Manus and the contamination paper are both right, about different content.

The cards nest, and the nesting changed in 2026. Production default: a state file (card three) for anything that crosses a boundary, harness reminders (card two) for standing constraints, failures kept as ruled-out lines (card five), a planner (card four) only once the executor is measurably paying for its own bookkeeping, and model recitation (card one) as the thing you reach for on a weaker model and remove when the eval says the model no longer needs it. Retrieval (1.4) decides what enters; compaction (1.3) decides what stays; notes decide what a reader who has neither will still know.

The load-bearing question is the first one, and it is the question 1.3 taught you to ask about compaction pointed at a different move: if a reader will arrive with less than the writer has now, the note has to survive the trip, so it lives outside the window and it is shaped by the preservation list. Everything below question 1 is about the cheaper problem, a reader who has the transcript and attends to it badly. Question 5 is the one that changed in 2026: the threshold at which model recitation stops paying for itself moved, because the models got better at holding a plan without being told to write it down, and Manus's one-third number is the specimen of what it looks like when you cross it.

5Seen in the wild

Anthropic's long-running coding harness is the best specimen because it was published twice, four months apart, with the second version explaining what it removed and why. The November 2025 harness is card three built out in full, on Sonnet 4.5 and then Opus 4.5. An initializer session writes the environment: feature_list.json, all features failing; claude-progress.txt; init.sh; a first commit. Every coding session runs the same four-line ritual: pwd, read the progress file and the git log, read the feature list and pick one, run the dev server and a smoke test, then work one feature, commit, and update the progress file. Between sessions the harness did a hard context reset, not compaction, because Sonnet 4.5 showed what the March post calls "context anxiety," wrapping up prematurely as it believed it was nearing its limit; a summary kept the anxiety, a clean slate did not. The failure-mode table in the post is a note-design table: declared victory early, so a feature list; undocumented progress, so a progress file plus commits; marked done prematurely, so a passes field it may only flip after testing; wasted time figuring out how to run the app, so init.sh. Each note has a named reader and a named field.

The March 2026 version (Rajasekaran, Anthropic Labs) is what happened when the models moved. Opus 4.5 "largely removed" context anxiety, so the resets went and the build ran as one continuous session under automatic compaction. Opus 4.6 held a plan well enough that the sprint decomposition went too, and the evaluator moved from per-sprint to a single pass at the end. What did not go: the planner (without it the generator under-scoped), the state files (agents communicate by writing a file the other reads), the sprint contract written before any code, and the evaluator, which "is worth the cost when the task sits beyond what the current model does reliably solo." The solo run took 20 minutes and $9 and shipped a game you could not play; the full harness took six hours and $200 and shipped one you could. Read it through 0.4: the hard reset and the sprint chunking were substitutions for a capability the model lacked, and the next two models ate them; the files, the contract, and the skeptical reader survived, because they are continuity and verification, not capability.

Aside: Claude Code's Tasks are the state file shipped as a product (on disk, dependency-aware, surviving compaction), and the fact that they now default off on the newest models is the November-to-March story compressed into a config flag.

The misconception "The todo list is what keeps an agent on task, so every agent needs one." What kept Manus on task in July 2025 was recency, and recency is a capability substitute: the executor was paying a third of its actions for it by October, and the newest models get most of the effect for free, which is why Claude Code turned the task tools off by default for them. The opposite error is the one to hold in the other hand: "so notes are obsolete." The reader on the far side of a boundary still arrives with nothing, Anthropic's harness still starts every session by reading a file, and Opus 4.6 still missed a blatant attack 31% of the time when it sat behind 800k tokens until a reminder was inserted. Model progress ate the recitation habit. It did not eat the file, the schema, or the reminder, because those serve a reader the model cannot become by getting smarter.

6Check yourself

Overnight coding run on a 400-file repo. The agent has retried the same failing database migration four times; the engineer wants to clear the errors from context "to give it a fresh mind." Approve, modify, or refuse?

Modify. Clearing the whole failed attempts is the right instinct; the contamination fit says a retry carrying four wrong diffs and the reasoning that defended them is running at a several-times-higher per-step error rate, and clean restart strictly dominates. But clearing the failures too is how you get attempt five identical to attempt four. Do card five properly: before the reset, write one ruled-out line into the progress file (migration X fails with error Y; hypothesis Z tested and wrong), then reset, then start the next window with the file read first. That is 1.3's fourth preservation class and Anthropic's session ritual doing the same job. Question 3 in the tree routes here because the failure was repetition, not drift.

Support agent, 30-turn conversations, loses the order number by turn 25 (1.2's question, now with a name). The team proposes having the model rewrite a full "case summary" at the end of every turn. Which card, and what would you change?

They proposed card one, and Manus's number is the warning: a full rewrite every turn spends an action and an append per turn on bookkeeping for a model that mostly does not need it. Use card three at short range: a small schema-shaped state block (order number, customer id, decisions made, open question) that the model updates only when a field changes, stored outside the transcript and selected back into a fixed position by the harness each turn. 1.2 called that write-then-select; this lesson adds the schema so the model updates fields rather than prose, and the harness owns the placement so recency is exploited without the model reciting. If the model still drifts on standing rules (tone, refund policy), that is card two, a static reminder, not a rewritten summary.

This tutor. It has a learner profile, a lesson ledger with open threads, a forward-references section, and a rule that every run starts by fetching the Notion hub and reconciling it against the installed files. Which card is each, who is the reader, and where is the one-third risk?

All of it is card three, at the longest distance: the reader is a future instance of the tutor with no memory of this session, so the notes are schema-shaped (mental model verbatim, badges, anchor, sources, open threads with target IDs) and written once per run at the boundary, not every step. The Notion hub cross-check is 1.3's recovery decision: the file is the bet and the archive is the log that catches it losing, which it did this morning, one lesson behind. The one-third risk would be if the tutor rewrote the ledger after every paragraph it drafted; it does not, and it should not, because the reader is not the next step, it is the next session. The open-threads lines are the ruled-out class pointed forward: what this lesson deliberately did not cover, written down so the next reader does not rediscover it.

Done when Module 1's bar: given any agent misbehavior, your first three hypotheses are all context hypotheses, and they are usually right. This topic's contribution: when an agent "forgot the goal," "declared victory early," "redid finished work," or "retried the same failure," ask who wrote the note it needed, how far away the reader was, and whether the note was rewritten into the window or read back from a file; then name the card the fix lives in. 1.1 supplied the budget, 1.3 the preservation list, 1.4 the locator, 1.6 supplies select for procedures, and 1.7 prices every rewrite.
