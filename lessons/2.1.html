The vocabulary: working, episodic, semantic, procedural

Name the question a memory will answer before you decide where it lives.

Freshness-checked 2026-11-11 · builds on 0.4, 1.1, 1.3, 1.5, 1.6, 1.7 · opens Module 2 · ~13 min read

1Why this exists

Module 1 was about one session. Everything in it, the attention budget, the four moves, compaction, notes, skills, the cache, assumed the window would eventually close and that was fine. Then products started needing the agent to be better on Tuesday because of what happened on Monday, and "the window closes" stopped being fine.

The first answer was one store. AutoGPT bolted a vector database onto its loop in 2023 (0.4 left that thread for 2.8), and a generation of agents copied the shape: embed everything the agent saw or said, retrieve the top few by similarity, paste them back in. It failed in a recognizable way. Ask such an agent for dinner ideas and it retrieves "the user said they are vegetarian" and "the user ordered steak for a guest on March 2" with nearly the same score, because both are about the user and food. One is a standing fact. The other is a one-off event. The store had no way to know the difference, so the ranking could not either.

The fix arrived as vocabulary before it arrived as architecture. CoALA (Sumers, Yao, Narasimhan, Griffiths, 2023) borrowed four words from cognitive science and gave builders a way to say what kind of thing they were storing. Ep 11 ended on exactly this teaser: is your agent's memory one thing or four? This lesson is the answer, and the reason the answer is "four questions, not four boxes."

2The mental model

Carry this out of the room A memory type is not a place to store things; it is a question the agent will ask its past: what am I doing (working), what happened (episodic), what is true (semantic), how do I do this (procedural). Each question needs its own write rule and its own way of being found, so one index that answers two of them answers both badly.

Read the four as questions and the rest follows. The question decides when you write (every step, every event, only when something is learned, only when someone reviews it), what shape the record takes (a window, a timestamped log, a fact with a validity, an instruction), how it goes stale, and what key you look it up by.

The last column is the point of this lesson's placement. You already own three of the four types; you just learned them as context moves. Working memory is the window, and 1.1's rule still governs it. Procedural memory is 1.6, verbatim:

From 1.6"A skill is the locator-and-payload move applied to instructions instead of data: the description stays in the window as a locator, the procedure stays on disk as a payload, and the whole design lives or dies on whether the description fires at the right moment."

And the episodic layer is 1.5's farthest reader made permanent:

From 1.5"A note is a message from the agent to a later, poorer-informed version of itself; how far away that reader is decides what the note carries and how often it gets rewritten."

Memory is the case where the reader is in another session entirely. What Module 2 adds is the semantic layer, the one with no Module 1 ancestor, and the discipline of keeping the four apart.

The cardinal rule

Do not mix memory types in one index with one retrieval strategy. Not because the categories are sacred, but because the four questions disagree on three things at once. Episodes are never wrong about the past, so you append and never overwrite; facts must be overwritten when they change, or the old one keeps winning. Episodes are found by time ("last week's deploy"), facts by entity ("the user's diet"), procedures by trigger ("when asked to deploy"). And they go stale on different clocks. Put two in one index and the ranking has to pick one of those behaviors for both.

There is a fresh, first-party demonstration of this. In Anthropic's Nov 6 memory post, a consolidation job writing contract facts into one shared table lost facts to overwrites; when the instruction changed to one page per contract, the share of graded contract facts captured went from 72% to 100%. Same model, same corpus: the only change was not making two kinds of record share one slot.

Why the write is the hard part

From 1.3"A compaction is a bet, placed by something that cannot see the future, on what a future window will need."

Every memory write is that bet moved to write time, and with a much longer horizon. Anthropic's post says it in four words: "Memory is, occasionally, a prediction." Their evidence that the bet is hard: an older model playing Pokemon wrote 413 files across 225 folders (per battle, per item) and drowned in stale state; a newer one wrote about ten files of strategy and rules the game never states, and got further. Steering mattered more than rules: telling the model what memory is for beat a fixed "record only failures" rule, which reduced memory gains on every model they tried. The type vocabulary helps exactly here. "Which of the four questions will this answer later?" is a better write test than "is this important?"

3The landscape

A landscape of: where a memory system keeps the difference between kinds of memory.
What varies: where the type distinction lives. Nowhere (one store); in the schema, decided at write time (typed stores); in position, decided by how high a record is promoted (a hierarchy); in a background process that converts one kind into another (consolidation); or in the weights (parametric). Five answers, ordered from the oldest to the newest.
Reading the diagrams: gray is shared structure; teal is what makes this approach different from the one above it; the amber dot marks where it breaks.

One undifferentiated store Legacy

Everything the agent sees or says is embedded into one index and retrieved by similarity. The AutoGPT-era default, and still what "add memory" means in many tutorials. 2.8 gives it the full autopsy; here it is the baseline the other four cards are reacting to.

Wins: one component, no decisions at write time, works on day one. Costs: similarity cannot tell an event from a fact from an instruction, so a stale fact outranks the current one and a one-off episode gets treated as policy; nothing is ever overwritten, so contradictions accumulate.

Done right: a documentation assistant whose only memory is the docs themselves. When there is genuinely one kind of thing in the store, there is nothing to mix, and this is just retrieval (1.4).

Typed stores by kind Current

The CoALA split taken literally: separate stores for episodes, facts and procedures, each with its own write rule and retrieval key, plus the window as working memory. LangChain's LangMem names its memory semantic, episodic and procedural; Letta's core, recall and archival memory are the same instinct cut by position in the window (2.3 owns that lineage). This is the shape most design docs draw in 2026.

Wins: each question gets the right key and the right staleness rule; facts can be overwritten without touching history; procedures can be reviewed separately. Costs: someone has to label every write, and the label is a judgment call made in the moment; three stores means three retrieval paths competing for 1.1's budget.

Done right: a support agent with a customer profile table (semantic, keyed by customer), a ticket history log (episodic, searched by date and product), and playbooks as skills (procedural, fired by trigger). Nobody has ever wanted to find a refund playbook by cosine similarity to a complaint.

A hierarchy by position Ascendant

Organize memory by how far a record has been promoted, not by what kind it is. Anthropic's Nov 2026 post describes four layers: transcripts (a searchable log), memory notes (written by the model), representations such as linked wiki pages, and a small injected layer loaded into every new session. Claude Code's auto memory is the visible tip: only the first 200 lines or 25 KB of its MEMORY.md index are loaded. The four type words never appear in the post. The types have not disappeared, they have become positions: episodes stay at the bottom, facts get promoted into pages, the few procedures that apply everywhere reach the top.

Wins: one decision (how high?) instead of a type label; the top layer stays small, which is 1.1's budget and 1.7's stable prefix at once; anything can be checked against the transcript beneath it. Costs: a wrong note that gets promoted is injected into every session afterwards; the injected layer competes with always-on instructions for the same seat (1.6's level 0).

Done right: a coding agent's memory folder: raw session logs, a handful of notes about the repo's quirks, one index file at the top. Small enough that the model can curate it, and every claim traceable to a session.

Consolidation as the type converter Current

A background process reads the episodic layer and writes the other two: facts distilled from many conversations, corrected notes, occasionally a new procedure. Letta and UC Berkeley named it sleep-time compute; OpenAI ships it in ChatGPT as Dreaming; Anthropic's Nov 2026 post is the first public description of Claude's version. The badge changed this year: in August this was ascendant, by November both big assistants run it in production (2.6 is the full lesson).

Wins: the hard write decision moves off the hot path to a moment with more information; facts get updated as time passes (a planned trip becomes a past trip); wrong notes get checked against transcripts. Anthropic measured a wiki built over 128 dreaming sessions on about 350,000 files going from 13% to 48% accuracy on its own, and wiki plus search at 61% against search alone at 53%. Costs: it consolidates errors as faithfully as truths; there is a lag before anything lands; it is compute spent on nobody's request.

Done right: a personal assistant with months of conversations, where the useful facts are scattered across hundreds of chats and none was ever stated as a fact.

Parametric memory Emerging

Experience trained into the weights instead of written to a store. Letta's memory-native RL work (Jun 2026) and the lab practice of training on agent trajectories are the live versions; Anthropic's post explicitly excludes weight changes from its definition of agent memory. Procedural memory is the type that fits here best, since a skill used a million times is a training signal.

Wins: zero context cost at run time; the procedure is just how the model behaves. Costs: you cannot read it, correct one fact, or delete one user's data; catastrophic forgetting is still the reason production avoids continual weight learning.

Done right: a lab folding the procedures its coding agent repeats across millions of sessions back into the next model, where nobody needs to inspect a single instance.

These nest the way Module 1's cards did. Working memory is always the window. Most real systems are card two or card three at the core, with card four running over it, and card five happening at the lab, upstream of you. Card one is what you build by accident when you skip this lesson.

As of this month. The vocabulary itself is now contested at the top. Anthropic's Nov 6 post builds the whole architecture by layer and never uses the four words. The big Feb 2026 survey (Huang et al., arXiv 2602.06052) keeps them, plus sensory memory, as one of three axes alongside substrate (weights, KV cache, external store) and subject (memory about the user vs memory about the agent's own work). And Hu et al. (arXiv 2512.13564) split by function into factual, experiential and working. Three framings, one agreement: what a memory is for has to be decided somewhere, and the disagreement is only about where.

4Choosing

When designing an agent, ask yourself these questions to decide how to keep its kinds of memory apart:

Question 2 is load-bearing because it is the write-time bet made explicit. If you cannot say whether a record will later answer "what happened," "what is true," or "how do I," no architecture choice downstream will rescue it; you will build card one by accident. Question 3 is the one whose answer moved in 2026: newer models curate a small folder well enough that the hierarchy, which needs no type labels, is now a serious option rather than a toy.

5Seen in the wild: ChatGPT memory

ChatGPT is the memory system with the largest user base, and you have used it, which makes it the right first anchor for Module 2. Read it through the four questions and every feature turns out to be one of them.

Working: the chat itself. Episodic: "reference chat history," which lets the model draw on past conversations without anyone stating a fact. Semantic: saved memories, the explicit facts written when the user says "remember that," and the synthesized memories that Dreaming produces in the background from many conversations. Procedural: the custom instructions and the preference types OpenAI separates out (how ChatGPT should respond, constraints, implicit preferences), which apply to every chat rather than being looked up. Dreaming is card four doing its job: it turns episodes into facts and keeps them current, so a July trip that was a plan becomes a trip that happened. OpenAI reports about a 5x compute cut, which is what lets them extend it to free users.

Read through 0.4. The first semantic layer, saved memories written on an explicit cue, is the part OpenAI now describes as going stale; it was the hot-path write, made by something that could not see the future. What survived and grew was the episodic log underneath and the offline process that converts it. That is 0.4's pattern in memory form: the write-time heuristic got eaten by a better process, and the log (the thing that makes correction possible) became more necessary, not less. The memory summary page, where users review and dismiss what the system believes, is the human gate on the semantic layer; 2.7 will argue it is also the only honest answer to deletion. Claude's memory, by Anthropic's own account, makes the same moves with different nouns: transcripts, notes, pages, an injected top layer, and dreaming between them.

The misconception "Episodic, semantic, procedural and working are the four boxes you build." They are four questions you design the writes and reads around. Anthropic's newest architecture has no box with any of those names and keeps them apart anyway, by position; a typed-store system can still mix them if every store is searched the same way. The opposite error is now tempting too: "Anthropic dropped the words, so the vocabulary is obsolete." The rule the words encode is exactly what their contract-table result showed: two kinds of record sharing one slot lost facts, separating them fixed it. Drop the labels if you like; never drop the separation.

6Check yourself

A personal finance assistant has to know the user's current salary, their past transactions, and their own rules for categorizing spending. The engineer proposes one vector database for all of it. What do you split, and how does each part get found?

Three questions, three behaviors. Salary is semantic: one record per fact, overwritten when it changes, found by key; in one index the old salary and the new one compete on similarity and the old one has more mentions. Transactions are episodic: append only, never edited, found by date range and merchant, which is a query, not a similarity search. Categorization rules are procedural: few, reviewed, applied on a trigger (a new transaction arrives), so they belong in instructions or a skill, not in a ranking. The one index would let "I used to make 90k" outrank the current salary and let one odd transaction look like a rule.

A month in, your coding agent's memory folder has 400 files and it keeps acting on notes that are no longer true. Which card are you on, what actually broke, and what is the first fix?

You meant to build card three and built card one in files: every write was saved, nothing was promoted or retired, so the folder is an undifferentiated store with directory names. The broken part is the write test (salience), the same failure Anthropic saw with 413 files. First fix: a small top-layer index with a hard size cap, and a consolidation pass (card four) that checks notes against session logs and deletes or demotes what no longer holds. Second: tell the model what memory is for; Anthropic found that beats rules like "record only failures."

A teammate says "we use a layered hierarchy like Anthropic's, so we don't need memory types." Where do the types still show up in a layered system?

In two decisions. At write time, the question "which of the four will this answer?" is still the best salience test. At promotion time, the type decides the destination: episodes stay in transcripts, facts get promoted into pages, and only procedures and standing facts that apply to every session earn the injected top layer. The hierarchy removed the labels from the schema, not from the reasoning.

Done when Module 2's bar: given a product description, pick a memory architecture, justify it against two alternatives, and name its failure modes before they happen. 2.1's share: for any product, list what it must remember, label each item with the question it will answer later, and name the failure that appears if two of them share one index (a stale fact outranks the current one, an episode becomes policy, a procedure gets retrieved in fragments). 2.2 to 2.5 supply the architectures to pick from; 2.6 and 2.7 supply consolidation and forgetting.
