Just-in-time retrieval vs pre-loading

Where the pointer lives, who resolves it, and why the coding agents that won hold a path in the window and read the file when a step asks for it.

Freshness-checked 2026-09-07 · builds on 0.2, 0.3, 1.1, 1.2, 1.3 · ~14 min read

1Why this exists

Your agent is dropped into a repository with three thousand files and asked to fix a bug. Somebody has to decide what it reads. The instinct inherited from chat is to load generously: paste the relevant directories, or run every file through an embedding model and stuff the top twenty chunks in before the first turn. In a single-turn exchange that instinct is rational. You get one shot at context, so you front-load, and the worst case is that the model ignores the excess.

An agent breaks that logic three times over. First, a loop re-sends its window on every step, so an unneeded chunk is not billed once, it is billed two hundred times (1.7 will send that invoice). Second, the excess is not ignored: 1.1 taught you that rot is a function of what is in the window, so every pre-loaded chunk that turns out to be irrelevant is paying negative rent on attention. Third, and this is the one nobody notices until a run is twenty minutes old, the repository keeps changing while the agent works on it. A file pasted in at step one is a snapshot; by step forty the agent has edited it, and the copy in the window is now a lie.

The deepest problem is epistemic, though. At step one, nobody knows what step forty will need. Not the harness, not a retriever, not the model. 1.3 gave you the vocabulary for exactly this situation: a compaction is a bet placed by something that cannot see the future. Pre-loading is the same bet, placed even earlier, before the task has produced a single clue about where it is going. Just-in-time retrieval is the discovery that the bet gets cheaper every step you wait, because each step reveals what the next one needs.

1.1 promised we would come back to the locator question: where does the pointer to a piece of data live, and who turns it into a payload. This is that lesson. 1.3 handed the select move to this topic and to 1.6; this topic owns select for data, 1.6 owns it for procedures.

2The mental model

Carry this out of the room Keep the locator in the window and the payload in the store: a pre-loaded payload is a relevance bet placed before step one, and a locator lets each step place that bet at the moment the need is actually knowable.

Three words are doing the work. A locator is anything small that names data without containing it: a file path, a symbol name, a URL, a stored query, a row id, a one-line description in a catalog. A payload is the data itself. The store is wherever the payload lives and stays true: the filesystem, a database, the web, an index built over one of those. The whole design space of this topic is a set of answers to two questions about the locator: where does it come from, and what resolves it into a payload.

This is 1.1's seat-price rule applied to the biggest tenant in the building. "Every token in the window spends from a finite attention budget, so the question is never 'does it fit' but 'does this token pay for its seat.'" A locator costs a handful of tokens and pays for its seat on every step, because it can be resolved at any time. A payload costs thousands and pays only on the steps that use it. Just-in-time retrieval is the policy that says: rent the seat to the locator, and bring the payload in as a guest.

It is also 1.2's select move with a rule attached. "Between two model calls the harness has exactly four moves on the window: move something out, bring something in, shrink what stays, or wall something off." Pre-loading is bring-in done once, at the front, by someone who cannot see the task. Retrieval is bring-in done repeatedly, by the step that knows what it needs. The rule this lesson adds is about timing: bring in as late as you can and still act. Anthropic's own phrasing of the approach is that agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools." That sentence is the CURRENT best practice in one line; the rest of this lesson is the option space around it and the evidence for where it bends.

One more consequence, because it is the one that surprises people who come from RAG. If the model holds the locator and the tools resolve it, then the model is the retriever. It decides what to look for, reads what came back, and decides again. The 2026 name for that is agentic search, and 0.3 told you why it works: filesystem plus bash are universal tools, so grep and cat are already retrieval tools if the model is good enough to drive them. Which raises the real question of this topic: what does the model need in its hand to drive them well, and when does it need an index under the hood?

3The landscape

What varies: how much data is in the window before step one (everything, a top-k slice, a map, nothing) and who turns a pointer into a payload (nobody, a pipeline, the model reading names, the model driving exact tools, the model driving an index). Five answers, ordered from most pre-loaded to least, with the resolver getting smarter as you go down.
Reading the diagrams: gray is shared structure; teal is what makes this approach different from the one above it; the amber dot marks where it breaks. The store is where data stays true; the window is the context.

Pre-load the payload Contested

Put the corpus in the window and let attention do the retrieval. You met this in 1.1 as "stuff the window," and the badge has not moved. The case for it got a real data point in January: on SagaScale, a long-context benchmark built from full novels, agentic retrieval beat naive retrieval on nearly every model, but when the text actually fit inside the model's window, long context beat agentic retrieval by 4.4 points on average, and by more on the million-token models. The case against it is 1.1's whole lesson plus a bill: LightOn (who sell retrieval, so weight it) measured retrieval at 8 to 82 times cheaper than long context across enterprise workloads, at roughly half the latency.

Wins: zero retrieval infrastructure; the model sees relationships a retriever would have cut; nothing to keep fresh because the whole thing is re-sent. Costs: paid on every step of a loop; rot scales with what is in the window, not what is left; the snapshot ages the moment the agent edits the store; a corpus that fits today does not fit after forty tool results.

Done right: one document that fits comfortably inside the reliable zone, read once, in a workflow with no loop: contract review, a single paper, one transcript. The condition is "fits and read once," not "fits."

Retrieve once, before the call Legacy

The 2023 pattern: embed the corpus, embed the query, put the top-k chunks in the prompt, call the model. Retrieval happens outside the loop, before the model has said a word, and the model never gets to ask a follow-up. This is what "RAG" meant for two years, and as an agent's retrieval architecture it is legacy for one structural reason: it places the relevance bet at the worst possible moment, with the least information, and gives the bettor no way to correct it. It survives everywhere as a subroutine (a search tool the agent calls is this pattern, one call at a time), so the vocabulary is still live; the architecture is not.

Wins: predictable token cost; one call; works with a model too weak to drive tools; the retriever can be tuned offline with a fixed eval set. Costs: a bad top-k is fatal because nothing downstream can notice it; chunking decides what the model can see; the index goes stale the moment the store changes; the query was written by a human, not by the step that needed the data.

Done right: a single-turn question-answering product with no loop and a stable corpus, where the question is the query and a citation is the deliverable. The moment you add a second step, this card is a tool inside one of the cards below.

Pre-load the map, retrieve the territory Current

Split the corpus into two representations. The locators (paths, names, one-line descriptions, a directory tree, a schema) are cheap enough to pre-load, so put a map in the window before step one. The payloads stay in the store and come in when a step names one. This is what Anthropic actually recommends in the September 2025 post: a hybrid, with some context computed up front for speed and the rest retrieved autonomously. It is also the pattern you already run without naming it: a CLAUDE.md that says where things are rather than what they contain, a skills catalog that loads names and descriptions always and bodies on demand (1.6 owns that half), Manus's todo file (1.5). The June act-context study drew the boundary this card lives on: given the same classes, natural-language summaries answered 9% of behavioral questions that the source answered 60% of the time, identically for a frontier summarizer and a 3B one. Compressed representations can tell you where to look; they cannot tell you what the code does. A map is for finding, and finding is a different job from acting.

Wins: step one starts oriented instead of blind; the map is tiny and cache-stable (1.7); every payload read is fresh; the map is human-editable, which is where most of the leverage over a coding agent actually lives. Costs: a stale or missing map entry hides a good payload; the map is a curated artifact and someone has to curate it; the same study found that summary-keyed hierarchical descent did not beat flat retrieval on its test set, so a fancier map is not automatically a better one.

Done right: any coding agent with a project file: tree plus conventions plus pointers, no file contents. The Agentless pipeline in section 5 is this card with the loop removed, so you can see the map and the territory as separate passes.

Agentic search over exact tools Current

No index, no map beyond a directory listing. The model drives grep, glob, find, an AST matcher, a language server, and reads what it finds, then searches again. The locator is whatever the model can name in the corpus's own words: a symbol, a string literal, a filename pattern. This is the pattern Claude Code shipped after trying the alternative; Boris Cherny has said the early versions used a local vector database and that agentic search "outperformed everything, by a lot," and Cat Wu's version of the reason is operational: embeddings have to be continuously re-indexed, and the same accuracy came with a much cleaner deployment story. Amp, Codex CLI, and Cline made the same call. The May 2026 CoREB benchmark explains part of why it works: the short keyword queries that agents actually emit ("auth flow," "handle error") collapse every embedding model it tested to near-zero ranking quality, so the query style that comes naturally to a model in a loop is precisely the style a lexical tool handles best. The structural layer is growing under this card rather than beside it: LARGER (May 2026) delivers graph evidence inside the lexical search result instead of through a separate graph tool.

Wins: nothing to build, nothing to keep fresh, nothing to secure beyond the sandbox you already need (7.2); always reads the current state, including uncommitted edits; exact, which matters for edits that must match verbatim. Costs: a vocabulary gap is a wall: if the word in the query is not in the file, grep returns nothing; more turns on large corpora, and every turn appends to the window; ContextBench measured that agents favor recall over precision and that much of what they explore goes unused, so the loop reads more than it needs.

Done right: a coding agent on a repository where the task names its own symbols, which is most tasks: a failing test, a stack trace, a function to change. The trace is the locator.

Agentic search plus a semantic index Ascendant

Same loop as the card above, with one more tool: a semantic search over an index that a pipeline keeps fresh. The model still holds the locators and still reads the payloads from the store; the index only answers "where might this be" when the model cannot name it. Cursor is the champion with numbers: after training its own embedding model on agent session traces (an LLM looks at a finished session and ranks what should have been retrieved earlier), semantic search alongside grep raised codebase question-answering accuracy by 12.5% on average, 6.5% to 23.5% depending on the model, with the gain concentrated on codebases over a thousand files. The same finding says where this card earns its cost: the query "where do we handle authentication" has to land on middleware/session.ts, a file the word never appears in. The CoREB caveat still applies (short queries collapse; off-the-shelf rerankers were net-negative on code across tasks), which is why the index is one tool in the loop rather than the retriever.

Wins: bridges the vocabulary gap; fewer turns on large corpora because the first hop lands closer; works on the sources grep cannot read: PDFs, tickets, diagrams, prose that describes code without naming it. Costs: an index is a second system with its own staleness, latency, and security boundary (your code leaves the machine, or you run the embedder); the gain shrinks below a thousand files; an untrained embedding model over code underperforms a trained one by a wide margin, so most teams get a weaker version of Cursor's result.

Done right: a monorepo where nobody knows the file names, or an enterprise document corpus where customers describe a problem in words the documentation never uses. Cursor at scale; a support agent over a help center.

The cards nest rather than compete. The production default is card three around card four: a map in the window, exact tools in the loop, payloads read fresh. Card five is card four with a tool added when the corpus earns it. Cards one and two are what the loop does inside a single step: read a whole file, run one search. Everything the loop reads still goes through 1.3's compactor eventually, which is why this topic and that one are the same discipline from two ends: retrieval decides what enters, compaction decides what stays.

4Choosing

When designing an agent, ask yourself these questions to decide how data gets into its window: pre-loaded, retrieved once, or retrieved per step, and with which locator.

Question four is where grep versus embeddings actually gets decided, and it is a question about the corpus and the task, not about the tools. If the task arrives with its own locators (a stack trace, a failing test, a symbol in the ticket), exact tools win and an index is a second system you pay for and do not use. If the task arrives in a vocabulary the corpus does not share (a customer's description of a bug, a product manager's name for a feature), no amount of grepping crosses that gap, and the honest options are an index or a hand-written map that translates. Notice that the not-yet leaf feeds question three: for most corpora, a curated catalog of a few hundred lines converts question four to a yes, which is why the map card is CURRENT and the index card is merely ascendant.

5Seen in the wild

Agentless (Xia, Deng, Dunn, and Zhang, University of Illinois, July 2024; FSE 2025) is the best place to watch this topic because its authors removed the loop on purpose. In 0.2's terms it is a fixed workflow: three phases, localization, repair, validation, with the model called at each step and no model-directed control flow. That makes it a specimen: every retrieval decision is a visible pipeline stage rather than a move buried in an agent's trajectory. And it mattered, because it matched the agent frameworks of its day on SWE-bench Lite at a fraction of the cost, and ContextBench (February 2026) evaluated it alongside SWE-agent, OpenHands, mini-SWE-agent, and Prometheus and concluded that sophisticated scaffolding yields only marginal gains in context retrieval, the paper's own "bitter lesson."

Its localization phase is the landscape drawn as a pipeline. It pre-loads a map: the repository's directory tree, paths only, and asks the model to name suspicious files from the names alone, which is card three with the model as the locator resolver. It also runs a dense retrieval pass (text-embedding-3-small) over the files, after asking the model to exclude irrelevant folders, and merges the two candidate lists: card five in miniature, an index consulted as a second opinion rather than as the retriever. Then it reads the chosen files as skeletons, class and function signatures without bodies, and asks the model to name the relevant elements. Only then does it load full bodies for those elements and ask for edit locations. Three passes, each one reading more of less: paths, then signatures, then code.

Two things to take from the specimen. First, the June act-context study explains why the skeleton pass sits where it does: signatures answered 13% of behavioral probes against the source's 60%, so a skeleton can locate an element and cannot support editing it, which is exactly the job Agentless gives it. Compressed representations are locators, not payloads, and the pipeline honors that boundary. Second, the amber dot is 0.2's rule applied to retrieval: with no loop, there is no verification of the localization bet, so a wrong file pick at pass one is carried to the end. Every agent in ContextBench's lineup is, in a sense, Agentless with a loop added so the bet can be corrected, and the paper's finding is that the loop buys less than you would think when the model is strong. That is 0.4's rule in retrieval clothes: the scaffolding that substituted for the model's ability to find things got eaten; the scaffolding that shaped what entered the window survived.

Aside: Claude Code is the same three widening reads (glob, grep, read) put inside a loop with no index, card four; Cursor is the same loop with a trained index underneath, card five; and the CLAUDE.md file that most of Claude Code's leverage comes from is the map, card three. The whole landscape is one pipeline with different choices about the loop and the locator.

The misconception "Claude Code beat RAG with grep, so embeddings lost." What lost was retrieving before the model could ask: the fixed pipeline, card two, with its bet placed at the worst moment and no correction. Embeddings survived as one locator among several, and the best public measurement of the question, Cursor's, found grep plus a trained index beat grep alone by 12.5%, more on large codebases. The subtler half of the error is why grep looked so decisive: CoREB showed that the short keyword queries a model emits in a loop are exactly the queries that collapse every embedding model, so grep did not win because it is smarter about meaning; it won because the loop's query style is lexical. Change the query style (a customer's paragraph instead of a symbol) or the corpus (documents instead of code) and the ranking flips. The durable lesson is the mental model, not the tool: hold the locator, resolve it at the step, and let the corpus tell you which resolver it needs.

6Check yourself

You are building a support agent over 40,000 help-center articles. The team proposes "RAG": embed everything and put the top five articles in the prompt before each turn. What do you change, and what do you keep?

Keep the index; the corpus earns it, because customers describe problems in words the articles never use (question four is a no) and the corpus is far past the size where a map alone converts it. Change the architecture from retrieve-once to a search tool the agent calls inside its loop: the model writes the query from what the conversation has revealed so far, reads what comes back, and searches again when the first hop misses, which is card five instead of card two. Pre-load a map anyway: the category tree and product names, a few hundred lines, so step one is oriented. And keep identifiers in context, not article bodies: the agent should hold "article 4471" and re-read it when a step needs it, so a compaction (1.3) loses a pointer and not the text. Measure precision as well as recall; ContextBench's finding that agents over-read applies here with a token bill attached.

Your coding agent runs on a 200-file repository. An engineer wants to add a vector index "because Cursor measured a 12.5% gain." Do you approve it?

Not yet, and say why with Cursor's own numbers: the gain concentrated on codebases over a thousand files and came from an embedding model trained on Cursor's own agent traces, which you do not have. At 200 files, exact tools plus a map cover question four for nearly every task, and the index buys you a second system (freshness, a security boundary, an embedder to run) for a gap you have not measured. The right sequence: write the CLAUDE.md map, give the agent grep, AST search, and a language server, and log the tasks where it fails to find something. If those failures cluster on vocabulary (the task said "auth," the file says "session"), you have the evidence for the index and the query set to evaluate it on.

A legal team wants an agent that answers one question per contract, 60 to 80 pages each, no follow-up questions, thousands of contracts a month. Someone has started building a retrieval pipeline. Is that the right call?

No. Question one is a yes: each contract fits comfortably inside the reliable zone, and each is read once for one question, so pre-loading the payload is the right card. The evidence is SagaScale's condition: when the text fits, long context beat agentic retrieval by 4.4 points, and a retriever that chunks a contract can cut the clause that qualifies the one it returned. The cost objection (LightOn's 8 to 82x) is real for a loop that re-sends the corpus every step and much weaker for one call per document. The moment the product adds follow-ups, or a question that spans contracts, you are back at question two with a yes, and the design changes.

Done when The Module 1 bar: given any agent misbehavior, your first three hypotheses are all context hypotheses, and they are usually right. 1.4's contribution is the select-for-data third of that: when an agent "couldn't find it," "read the wrong file," or "is slow and expensive on reads," you ask where the locator lived, who resolved it, and whether the payload arrived before the step that needed it, and you can say which card the fix lives in. 1.1 supplied the budget, 1.3 the compactor, 1.6 will supply select for procedures, 1.7 the bill.
