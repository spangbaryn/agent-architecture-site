Agent Architecture · Module 1 · Topic 1.6

Progressive disclosure and Skills

Decide where every piece of procedural knowledge should live, and defend why the description is the only part that pays rent.

Freshness-checked 2026-09-20 · builds on 0.3, 1.1, 1.2, 1.4, 1.5 · ~14 min read

1Why this exists

By the middle of 2025 the system prompt had become a landfill. Every team that shipped an agent learned the same thing in the same order: the model does a task wrong, someone writes the correct procedure into the prompt, it works, and six months later the prompt is nine thousand tokens of "if the user asks for a spreadsheet, do this; if the ticket mentions billing, do that." Each rule was added for a good reason and each rule is irrelevant on almost every turn. 1.1 named the bill: every one of those tokens spends from the attention budget on every step, whether or not this step is the one it was written for. 1.1's open thread said this rot "pushes case material into retrieved skills." This is where that thread lands.

Tools had the same disease with bigger numbers. Anthropic measured a five-server MCP setup at roughly 55,000 tokens of tool definitions for 58 tools before the agent had done anything, and reported internal cases where definitions alone consumed 134,000 tokens. 0.3 taught you that a tool surface is "a context-budget decision wearing an API costume." In October 2025 Simon Willison looked at this and wrote that Claude Skills were "maybe a bigger deal than MCP," and his stated reason was exactly the token bill: GitHub's official MCP server "famously consumes tens of thousands of tokens of context."

0.3 promised we would come back to this. Its ledger records that Claude Code kept its tool list short "below the level of the task" and moved specificity "into skills loaded on demand." 1.2 left "tool loadout vs progressive disclosure" for here. 1.4 and 1.5 both said "select for procedures" belongs to 1.6. Four debts, one answer: procedural knowledge is a payload, and 1.4 already told you what to do with payloads.

2The mental model

Carry this out of the room A skill is the locator-and-payload move applied to instructions instead of data: the description stays in the window as a locator, the procedure stays on disk as a payload, and the whole design lives or dies on whether the description fires at the right moment.

1.4's sentence was: "Keep the locator in the window and the payload in the store: a pre-loaded payload is a relevance bet placed before step one, and a locator lets each step place that bet at the moment the need is actually knowable." Read it again with "procedure" in place of "data" and you have this whole topic. A nine-thousand-token system prompt is a pre-loaded payload of procedures: a relevance bet on every one of them, placed before step one, on every turn. A catalog of one-line descriptions is a set of locators. The model reads the catalog, recognises that this task is the spreadsheet one, and pulls the spreadsheet procedure in. The procedure pays for its seat only on the turns that use it.

The field calls this progressive disclosure, and the Agent Skills format made it concrete as three levels. It is worth seeing them as five, because the two ends are where the design decisions hide:

LevelWhat it isWhen it enters the windowCost
0Always-on layer: system prompt, CLAUDE.md, AGENTS.mdEvery turnPaid every step, forever
1Catalog: name plus description from every skill's frontmatterEvery turnAbout 100 tokens per skill
2Body: the SKILL.md instructionsWhen the skill firesUnder 5k tokens, once, then it persists
3References: extra files the body points atWhen the body says to read themZero until read
4Scripts: code the body tells the model to runNever; only the output entersThe output's size, not the code's

Level 4 is the one people miss and it is the sharpest form of the idea. A 400-line script that renders a chart never costs 400 lines of context. The model sees a one-line instruction to run it and then sees the result. That is 0.3's "code execution over tool preloading" arriving as a file in a folder. Level 0 is the one people overuse, and the entire discipline reduces to a rule about what has earned a permanent seat there: standing constraints and conventions, the material 1.1 called altitude. Procedures almost never qualify, because a procedure is by definition relevant to some turns and not others.

Two things follow. First, the description is not documentation. It is the trigger, and the only part of a skill that is in the window when the decision to load it gets made. The Claude Platform docs require it to say both what the skill does and when to use it, and Claude Code truncates description plus when_to_use at 1,536 characters, so it is a locator with a hard size cap. Second, "skills versus MCP" was never a rivalry over what the model can do. It was a rivalry over how much sits in the window before step one, and by November 2025 the MCP side had made the same move: mark tools defer_loading and give the model a search tool, which cut one setup from about 77,000 tokens to about 8,700. Same move, different payload.

This tutor is itself the thing it is teaching, which is why you are reading it at all. Its description fired when you typed "next lesson." Its body loaded the workflow. Its references/ folder held your profile and the ledger until the workflow said to read them. Nothing about lesson 1.6 was in the window when you said hello.

3The landscape

A landscape of: where a procedure lives between uses, and what decides the moment it enters the window.
What varies: how much of the procedure is in the window before it is needed (all of it, one line, none of it), and who resolves that line into the full procedure (nobody, the model, a harness rule, a search tool, a separate agent). Five answers, ordered from most pre-loaded to most isolated.
Reading the diagrams: the dashed box is the context window; gray is shared structure; teal is what makes this approach different from the one above it; the amber dot marks where it breaks.

Always-on instructions Contested

Every procedure lives in the system prompt or a CLAUDE.md-style file and is in the window on every turn. Nobody resolves anything because nothing was ever taken out. This is the default every team starts with, and it is the correct home for one class of material: standing constraints and conventions that apply to every turn. The contest is over where that class ends, and in practice it ends far earlier than the file does.

Wins: zero mechanism, zero trigger risk, the model cannot fail to load what is already there. Costs: the bill from 1.1, paid on every step by every rule that does not apply to this step; the if-then rot that 1.1 flagged; and no way to add procedures without diluting the ones already there.

Done right: a two-hundred-line CLAUDE.md that says how the repo is laid out, what the test command is, and three things the team never does. Every line applies to every turn, which is the test. The moment a line starts with "when the user asks for," it has failed the test and belongs one card down.

Catalog plus on-demand body (Skills) Current

Each procedure is a folder with a SKILL.md. Only the frontmatter's name and description stay in the window; the model reads the catalog, decides a skill applies, and loads the body, which may point at further files and scripts. Anthropic shipped it in October 2025, published it as an open specification at agentskills.io in December 2025, and within days Cursor, Amp, Letta, goose, GitHub, VS Code, OpenCode and OpenAI's Codex had adopted the format. The model is the resolver: the same "the model is the retriever" consequence 1.4 drew for data.

Wins: procedures cost about 100 tokens each until used; the unit of improvement is a file you can diff, version and permission-gate (5.2 will make this the safe self-improvement channel); scripts run without their code ever entering context. Costs: the description is a bet the model places on every turn, and a mis-fire is silent: a skill that never triggers looks identical to a skill that does not exist. SkillsBench (Feb 2026, Li, Song et al.) found curated skills raised average pass rate 16.2 points but 16 of 84 tasks got worse, and skills the model wrote for itself added nothing on average.

Done right: the document skills Anthropic ships (pptx, xlsx, docx, pdf). Each is a whole domain's worth of gotchas plus scripts, none of it relevant until someone asks for a spreadsheet, at which point all of it is. The description "create, read, edit spreadsheets" is exactly as long as the trigger needs to be.

Harness-triggered loading Ascendant

The same folder of procedures, but a deterministic rule in the harness decides when a body enters, not the model. Claude Code's paths: frontmatter loads a skill only when the model touches matching files; nested .claude/skills/ directories load when work moves into that subtree; VS Code's .instructions.md files carry an applyTo glob; hooks fire on lifecycle events. This is 1.2's harness-triggered card wearing procedure clothes, and it is ascendant for the reason 1.5's harness reminders survived: a rule cannot forget.

Wins: triggering is exact and testable; nothing depends on the model reading a description well; it composes with the catalog card (a skill can have both a description and a path rule). Costs: the rule sees the file, not the intent. Editing billing.py to fix a typo loads the whole billing procedure. And there is no rule for procedures whose trigger is a kind of request rather than a kind of file.

Done right: a migration-safety skill with paths: "db/migrations/**". The moment any agent, on any model, opens a migration file, the checklist is in the window, and no description had to be good enough to make that happen.

Deferred tool definitions Ascendant

Progressive disclosure applied to capabilities instead of procedures. Tool definitions are marked deferred; the window holds only a search tool (about 500 tokens) and whichever tools are used constantly; the model searches for the rest by name or description and the matches expand into full definitions. Anthropic's Tool Search Tool (Nov 2025) reported the 77k-to-8.7k reduction above and, more interesting, an accuracy jump on MCP evals from 49% to 74% on Opus 4, because fewer definitions in the window means fewer near-identical names to confuse. That is 1.2's confusion failure mode fixed by its select move.

Wins: a large tool library with a small standing footprint; better tool choice, not just cheaper. Costs: a search miss means the tool does not exist for the model on this turn, and unlike a skill mis-fire this one can block the task outright. The tool is still a contract plus a prompt (0.3); deferring it moves the prompt half behind a search, so the one-line searchable summary now carries the load the full description used to.

Done right: an enterprise agent wired to GitHub, Slack, Jira and three observability servers. Nobody uses more than a handful of those 100-plus tools per task, and the handful changes per task, which is precisely the case where the standing footprint should be a search box, not a library.

Forked skills Emerging

The procedure never enters the main window at all. Claude Code's context: fork makes the skill body the task of a fresh subagent, with its own tool set and no conversation history; only the result returns. VS Code's custom agents have the same shape. This is 1.2's isolate move, and it is the endpoint of the axis: not "load it late" but "load it somewhere else."

Wins: a noisy procedure (a 40-step review that reads half the repo) cannot poison the parent's window; the subagent can have a narrower tool set and a different model or effort level. Costs: the handoff loses context, in both directions. The subagent does not know what the conversation already decided, and the parent gets a summary, which 1.3 taught you is a bet. Module 4 sends this card its full bill.

Done right: a code-review skill that runs in a forked Explore agent while the main session keeps working. The review needs to read widely and the parent needs none of that reading, only the verdict, which is the verification-subagent shape 4.3 will formalise.

These nest rather than compete. The production default in 2026 is a short always-on layer, a catalog of skills under it, path rules on the skills whose trigger is a file, deferred tools once the tool count passes a few dozen, and a fork for the one or two procedures that read more than they decide. One thing that does not nest: a second catalog level. He et al. (Jul 2026) ran the first controlled comparison and found single-level progressive disclosure pulled ahead on multi-document tasks while "adding a second routing level provided no benefit and sometimes reduced accuracy." A skill whose job is to list other skills is a description that has to fire twice.

4Choosing

When designing an agent, ask yourself these questions to decide where a piece of procedural knowledge should live:

Question 4 is the load-bearing one because it is the bet. Questions 1 through 3 route material to places where nothing has to be recognised: it is always there, it is a tool the model searches for by need, or a rule fires on a path. Everything that survives to question 4 will enter the window only if the model reads a one-line description on a busy turn and decides this is the moment. If you cannot write that line so that it fires on the right requests and stays quiet on the rest, you do not have a skill yet; you have a document, and the honest options are to keep working on the line or to let a human invoke it by name (disable-model-invocation) until you can. Question 5 is the one that changed in 2026: forks were a subagent feature and became a frontmatter field, which turns "should this run in isolation" from an orchestration decision into a per-procedure one.

5Seen in the wild

VS Code's Copilot agent is the cleanest place to watch this landscape, because Microsoft shipped every card as a separate file type and then, in 2026, retired one of them in favour of another. Read its customisation layer as the five levels and the five cards at once:

Always-on: copilot-instructions.md, and the same slot now reads AGENTS.md and CLAUDE.md, which tells you the always-on layer has become a cross-vendor convention rather than a product feature. Card one, and Microsoft's own guidance is the card's rule: use the narrowest scope that fits.

Harness-triggered: .instructions.md files carry an applyTo glob and enter the context only when a matching file is in play. Card three, shipped before the skills format existed, which is a small piece of evidence that path rules are the older and more conservative half of progressive disclosure.

Catalog plus body: Agent Skills, in the open SKILL.md format, discovered by the model from their descriptions. Card two.

The badge change: VS Code had a separate "prompt files" type, invocable by slash command, with its own description-based triggering. In 2026 the docs marked them deprecated for agent sessions and told users to convert them to skills. Claude Code did the same with custom slash commands, folding .claude/commands/ into skills. Two vendors independently collapsed "a reusable prompt you invoke" into "a folder the model can load," and the difference between the two things was never the prompt. It was the directory: references and scripts at levels 3 and 4, and frontmatter that can carry a trigger rule. A prompt file is a skill with only level 2.

Fork: custom agents, selected explicitly, with their own tool sets. Card five, the endpoint of the axis, and in VS Code it is still a user choice rather than a skill's own frontmatter, which is why the card is emerging and not current.

Read the whole layer through 0.4's rule. The parts that substituted for model capability, a separate prompt-file type and its separate trigger, got absorbed. The parts that shape what enters the window and when, the always-on file, the glob rule, the catalog, the fork, survived and converged across vendors. Claude Code, as a one-line aside: the same convergence from the other direction, with the extra data point that after auto-compaction it re-attaches the last 5,000 tokens of each loaded skill under a shared 25,000 token budget, which is 1.3's exemption list applied to procedures.

The misconception "Skills replaced MCP." Willison's line launched a thousand takes, and almost all of them read a token-cost comparison as a capability comparison. A skill tells the model how to do something. A tool lets it do something it otherwise cannot. The pptx skill is useless without a shell; the GitHub MCP server is expensive without a skill that says which six of its tools matter for a release. What Willison actually attacked was pre-loading, and MCP fixed that within six weeks by deferring definitions behind a search tool. Progressive disclosure is a move, not a product; skills are the move applied to procedures and deferred tools are the move applied to capabilities. The opposite error, held in the other hand: "progressive disclosure makes the agent smarter." He et al. found its gains were "near zero when a strong agent harness already divides and retrieves on its own," and SkillsBench found models cannot write the skills they benefit from. It buys context, not intelligence. What it does with the context it buys depends entirely on what someone curated into the body.

6Check yourself

You are building a support agent with forty internal procedures (refund rules, escalation paths, tone guides, the outage playbook). An engineer says "it's 30k tokens, it fits, put it in the system prompt." Which cards, and why not the single card he proposed?

Split it by question 1. The tone guide and the three things the agent must never promise apply on every turn: always-on. The thirty-odd procedures do not; each applies to some tickets and rots the rest, so they become skills with descriptions written as triggers ("use when the customer disputes a charge"). The outage playbook is the interesting one: its trigger is not in the customer's words but in the system's state, so give it a harness trigger (an incident flag) rather than a description. "It fits" answers the wrong question; 1.1's question is whether each token pays for its seat on this turn, and a refund procedure loaded into a password-reset ticket does not. Bonus: the refund procedure is the one whose action is irreversible, so it is also the one to mark user-invoked-only until 4.7 gives you a better gate.

Your agent has 120 tools across six MCP servers and one skill that describes the release process. It is slow before it starts and it keeps picking create_issue when it should pick create_pr. What do you change first, and what stays?

Defer the tools. The 120 definitions are the pre-loaded payload and the near-identical names are 1.2's confusion failure mode; Anthropic's numbers say deferring both cuts the standing footprint by most of its size and improves selection, not just cost. The release skill stays, and it gets better: its body can now name the six tools the release needs, which turns the skill into the map and the tool search into the territory, 1.4's card three around card four. What you do not do is delete the skill because "the tools are the capability." The skill is what stops the model from having to rediscover the release procedure from 120 tool names every time.

A team's skills fire too often on some requests and never on others. One proposal is a "router" skill whose body lists all the other skills and says when to use each. The other is to rewrite the descriptions. Which, and what evidence?

Rewrite the descriptions, and measure them. He et al. tested exactly the router idea as a second routing level and found no benefit and sometimes worse accuracy; a router skill is a description that has to fire correctly twice, and the second firing happens with the first skill's body already spending budget. The description is the only thing in the window when the decision is made, so it is the only lever. Treat it as a trigger to be tested, not prose to be polished: build a small set of requests that should and should not fire it, and run them. If some skills still will not trigger reliably, that is question 3 or question 4's not-yet leaf: give them a path rule, or make them user-invoked until the line is right.

Done when Module 1's bar is that any agent misbehaviour produces three context hypotheses first, and they are usually right. 1.6's contribution: when the complaint is "it ignored our process," "it is expensive before it starts," or "it picked the wrong tool," you reach for the procedure's address before its wording. Was it always-on and rotted? Was it a skill whose description never fired? Were a hundred tool definitions in the window competing with the six that mattered? And you can say, for any procedure someone hands you, which of the five cards it belongs in and which frontmatter line makes that true. 1.7 supplies the missing half of the bill: what each of these loads and reloads does to the cache.
