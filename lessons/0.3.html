Tools and tool design

Decide what an agent's hands should look like, and why fewer is usually more.

Freshness-checked 2026-08-21 · landscape rebuilt 2026-08-22 with per-card diagrams · builds on 0.1, 0.2 · ~12 min read

1Why this exists

A model that can only emit text cannot check anything. Tool calling closed that gap, and then opened a new one: every tool you hand the model is text it reads every turn before it does anything, and a surprising share of agent failures turn out to be the model picking the wrong tool, calling it wrong, or drowning in what it returned. Tool design exists because the interface between a deterministic system and a non-deterministic one has two sides, and most teams only design one.

2The mental model

Carry this out of the roomA tool is two things at once: a contract with a deterministic system, and a prompt aimed at a non-deterministic one. Most bad tools are bad because someone only designed the first half.

The contract half is ordinary API design. The prompt half is the one that gets skipped: descriptions, parameter names, example values, and error text are all tokens the model reads while deciding what to do. An error saying 400 Bad Request teaches nothing; one saying start_date must precede end_date; you passed 2026-08-21 and 2026-08-01 lets the model fix itself next turn.

Three rules follow. Consolidate: if the model must reliably call three tools in a fixed order, that ordering is your job, not its judgment call. Namespace: ambiguity between two tools called send is a coin flip you paid for. Return signal, not payload: a tool that dumps 40,000 tokens of JSON has spent the attention budget on fields nobody reads.

3The landscape

A landscape of: what the agent's tool surface looks like: what sits between the model and the world, and what it costs in context per turn.
What varies: how general the tools are and where the composition happens, from a short hand-curated list, to one universal tool, to tools called from generated code. Four answers, three of them live; the fourth is the anti-pattern most teams start with.
Reading the diagrams: gray is structure every approach shares; teal is the element that makes this approach different from the one above it; the amber dot marks where it breaks.

The curated tool set Current

Five to fifteen tools, each shaped around a complete job, descriptions rewritten by watching the agent misuse them. Anthropic's "writing effective tools" guidance.

Wins: predictable, enumerable, fits behind approval gates. Costs: every new capability is human work.

Done right: A customer-support agent with eight tools: look up order, check policy, issue refund, escalate, and so on. Each one is a whole job, each description was rewritten after watching the agent misuse it, and the irreversible ones sit behind approval. The surface is small enough to audit line by line.

Filesystem plus bash as the universal tools Current

Give the agent a computer instead of an API surface. Microsoft's SRE agent moved from over a hundred bespoke tools to files and raised intent-met on novel incidents from 45% to 75%.

Wins: unreasonably general, composes without anyone designing the composition, doubles as memory. Costs: enormous blast radius, so sandboxing is mandatory.

Done right: Incident investigation on a cloud service. Microsoft's SRE agent replaced over a hundred bespoke query tools with a filesystem and a shell: the agent greps logs, runs ad-hoc scripts, and leaves notes for the next turn, inside a sandbox with read-only production access.

Code execution and programmatic tool calling Ascendant

The agent writes code that calls your tools; definitions live as importable files, results are processed in the runtime and only conclusions return to context. Roughly 98% token reduction on tool-heavy workloads.

Wins: loops and joins happen in code where they are cheap and correct. Costs: needs a sandboxed runtime; debugging shifts to reading generated code.

Done right: An analytics question that spans three APIs: the agent writes one script that pulls ten thousand rows, joins and aggregates them in the runtime, and returns a five-line summary. The context never sees the rows, only the answer.

Preload every MCP server you have Legacy

Connect everything and let the model sort it out. The 2025 default, and the source of most "our agent got worse when we gave it more capabilities" reports.

Wins: none worth naming. Costs: pays for every definition every turn, invites confusion between near-duplicate tools, burns the budget before the task starts.

Done right: As a discovery spike only: connect everything for an afternoon, run the real task twenty times, and log which six tools the agent actually reaches for. Then disconnect the rest and curate those six. The pattern is correct for one afternoon and wrong for one deployment.

The gating question wins because approval gates need a tool you can name; you cannot put a human in front of "bash." If nothing needs gating, the question becomes whether you can predict the composition: when you can, curate; when you cannot, give the agent a computer, and move to code execution once the work is dominated by data the context should never see. Preloading everything survives only as a way to discover the curated set.

5Seen in the wild

Claude Code's tool list is short and deliberately below the level of the task: read, write, edit, bash, grep, glob, web fetch. There is no create_pull_request primitive, because a shell already does that and each such tool would be a bet about how a specific project works. The specificity moved into skills instead: procedural knowledge in files, loaded when relevant, rather than tools in context loaded always. In the cards above, that is the second shape with a thin layer of the first.

The question to ask before adding any tool: is this a capability the agent lacks, or a workflow I am encoding because I do not trust it to figure the workflow out? The second is usually a skill, a prompt, or a piece of your own harness.

The misconceptionThat more tools mean a more capable agent. Past a small number, each tool costs attention every turn and adds a chance of picking the wrong one, so capability and tool count come apart quickly. A tool surface is a context-budget decision wearing an API costume. Ask what it costs per turn, not just what it unlocks.

6Check yourself

Your agent reliably calls list_customers, get_customer, get_orders, and get_order_items in sequence to answer one question. Fix?

Consolidate. That fixed sequence is a join you made the model perform across four turns, paying context for each intermediate. If the joins vary too much to fold into one tool, move to code execution and let the agent write the join.

You are adding a payments MCP server with forty tools to an agent that has eight. What first?

Do not connect all forty. Expose the few it needs, or put the server behind code execution so definitions load on demand. Separately, treat the irreversible ones as a permissions problem: gate the actions, not the reasoning. Two distinct failure modes, context dilution and blast radius, needing different fixes.

An agent keeps passing malformed arguments to one tool. You have rewritten the description twice. What else?

The error message and the parameter shape. Errors are prompts. And if a parameter is easy to get wrong, that is a design smell: constrain the type, supply an enum, take a natural key instead of an opaque ID. Make the wrong call hard to express rather than explaining it again.
