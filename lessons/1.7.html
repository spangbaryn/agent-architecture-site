Agent Architecture · Module 1 · Topic 1.7

KV-cache economics

Why the order of your context window is the biggest line on your agent's bill, and how to lay a window out so it only ever changes at the end.

Freshness-checked 14 October 2026 · builds on 1.1 through 1.6 · last lesson of Module 1 · ~15 min read

1Why this exists

An agent spends most of its life re-reading. Every step sends the whole window so far, tools, system prompt, every earlier tool call and result, plus a little that is new, and gets back a short answer. Manus measured about 100 input tokens for every output token. In the worked example below it is 200 to 1. Read naively, that makes the cost of an agent grow with the square of its step count, because step 60 pays for steps 1 through 59 all over again.

Here is the physics that rescues it. When a model reads your prompt, it computes for every token a set of keys and values that later tokens attend to. That computation (the "prefill") is the expensive part of reading, and each token's values depend only on the tokens before it. So if the next request starts with exactly the same tokens, the provider can keep those values (the KV cache) and skip recomputing them. Change one token and every token after it has a different past, so everything after it must be computed again. Three rules fall out, and they are the whole subject: reuse is prefix-only, the match must be exact, and the stored values live briefly (five minutes by default on Anthropic, refreshed each time they are used; at least thirty minutes on OpenAI's newest models).

Providers pass the saving on, which turns a byte-level property of your prompt into a pricing tier. OpenAI's Codex team describes the effect as sampling becoming linear rather than quadratic. Claude Code's team says they build their entire harness around it and declare an incident when the cache hit rate drops. That is the pressure: long-horizon agents are only affordable if most of every request is a repeat of the last one.

As of this month The field notes this syllabus was written from (August 2026) said cached input costs about a tenth of fresh input. That is still true on most models, but the newest ones widened it: cache reads cost 0.05x the input price on Claude Opus 5.5, Sonnet 5.5 and GPT-6.1 Sol, and 0.025x on Claude Fable 5.1 and Mythos 5.1. The gap went from 10x to 20x and 40x. Everything in this lesson got more important, not less, between the syllabus and today.

2The mental model

Carry this out of the room The cache bills you for change, not for size: every token up to the first one that differs from the last call is nearly free, every token after it is paid in full, so a cheap agent is one whose window only ever changes at the end.

Three consequences, each worth saying out loud in a design review.

Position is price. On Opus 5.5 a fresh input token costs $4 per million, writing it into the cache costs $5, and reading it back costs $0.20. The same token is twenty times cheaper if it sits before the first change than after it. Where a token sits in the window now matters more to the bill than whether it is there at all.

An edit costs everything downstream of it. Changing a line at the tail costs the tail. Changing a line near the top costs the whole window, because every token after it has a new past. "Small edit" is not a property of the edit; it is a property of where the edit lands.

A broken cache costs more than no cache. Writing into the cache costs 1.25x the base price on Anthropic and on OpenAI's GPT-5.6 and later. If something at the top changes on every call, you pay that premium every call and never collect a read. The chart below runs the same sixty-step agent five ways.

That last row and the first one say the same thing from two sides, and it is worth naming because it is the one place this lesson argues with 1.1. There are two budgets. The attention budget (1.1) prices relevance: does this token pay for its seat. The cache prices position: did this token move. Always-on instructions are cheap in dollars and expensive in attention; a compaction is cheap in attention and expensive in dollars. Most bad agent economics come from optimizing one budget while the other one quietly sends the bill.

And Ep 10 left a question hanging: is the cheapest procedure the one you never load, or the one you never move? The cache answers it. The one you never move. Claude's tool search keeps deferred tools out of the prefix and expands a discovered tool inline in the conversation, so, in the docs' words, "the prefix is untouched." A skill body read mid-session is appended the same way. What costs is pruning the tool list per phase or editing the catalog: that is a change at the top, and the top is where every token after it gets re-billed.

3The landscape

A landscape of: how a harness lays out the window and makes its changes, so that each call re-pays as little of it as possible.
What varies: where in the window change is allowed to happen. Anywhere; only at the tail; at the tail, by translating state changes into appends; in the middle, but only at declared seams; or anywhere, because you run the cache yourself. Five answers, ordered from most of each call re-paid to least.
Reading the diagrams: each shows the window on two consecutive calls. Light fill is read from the cache; white is paid in full; teal is what makes this approach different from the one above it; the amber dot marks where it breaks.

Cache-oblivious window Legacy

The prompt is rebuilt every call from current state: a timestamp or session header at the top, a tool list filtered for the current phase, retrieved chunks injected into the system prompt, history edited in place to stay tidy. Nothing matches from one call to the next. This was how 2023 and 2024 frameworks assembled prompts, and it is still what you get by accident when nobody is watching the hit rate.

Wins: the simplest mental model there is; the prompt always states exactly the current truth; nothing to monitor. Costs: every call pays full price for the whole window; with caching switched on it pays the 1.25x write premium for nothing (the $30.37 row above, worse than no cache at all); time to first token never improves, so the agent also feels slow.

Done right: a one-shot router or classifier on short prompts, under the minimum cacheable length (512 tokens on Claude's 5.5 models, 1,024 on OpenAI's newest), or a batch where every request is genuinely different. If nothing repeats within the cache lifetime there is nothing to protect, and a cache-oblivious prompt is simply the honest one.

Append-only window, stable prefix Current

Order the window from least to most volatile (tools, system prompt, durable project docs, then the conversation) and never edit anything already sent: new state arrives as a new message at the end. Manus wrote the playbook in July 2025 (stable prefix, append-only context, deterministic serialization, an explicit breakpoint at the end of the system prompt). OpenAI's Codex and Anthropic's Claude Code both published the same shape in 2026; Claude Code layers it so the top is shared as widely as possible: system prompt and tools cached across everyone, CLAUDE.md per project, session context per session, then messages.

Wins: cost becomes linear in steps instead of quadratic, and latency drops with it; the window is naturally a replayable log (1.2's "log is truth"). Costs: the window only grows, so it runs straight into 1.1's attention budget and, eventually, 1.3's compaction; anything that truly must change near the top (the tool set, the model, a wrong fact) costs the whole window; the silent breakers are invisible without monitoring: a JSON serializer that does not guarantee key order, an MCP server that enumerates its tools in a different order on reconnect.

Done right: when you change Codex's sandbox mode mid-session it appends a new permissions message instead of editing the original, and when you change directory it appends a new environment-context message. The old messages stay wrong and stay put; the newest one wins.

Change by appending Ascendant

Card two's discipline stretched over the things that look like they must change at the top: the current time, the mode, the permissions, the available tools. The harness translates each one into an appended signal. A reminder inside the next user message (how Claude Code tells the model the date or that a file changed). A mode the model enters by calling a tool (Claude Code's plan mode). A mask over an unchanged tool list (Manus's decoding-level state machine; OpenAI's allowed_tools). A system message or a tool definition sent mid-conversation (Anthropic's mid-conversation system messages and tool_addition blocks). The delta from card two: nothing about the agent's state is allowed to live in the prefix.

Wins: keeps card two's bill while the agent changes mode, gains tools, and learns the time; as of September and October 2026 both major APIs ship these as request fields rather than harness craft, which is why the badge is rising. Costs: everything stays visible, so masked tools still spend 1.1's attention, and a mask only holds if it is enforced in decoding or by the API (a prompt saying "don't use X" is a request, not a mask); some switches still re-pay part of the window (on Anthropic, changing tool_choice keeps the tools and system cache but re-pays the messages); the primitives exist only on newer models.

Done right: Manus keeps one tool list for the whole task and names tools with shared prefixes (browser_, shell_), so "only browser tools in this state" is a constraint on decoding, not an edit to the definitions.

Segmented prefix with seams Current

Accept that some moves must edit the middle (1.2's write and compress, 1.3's compaction, clearing old tool results) and engineer where and how often they happen. Put explicit cache breakpoints at the boundaries of stability (after tools and system prompt, after project docs, on the compaction block) so a change re-pays only what lies after the seam. Make edits rare and big: Anthropic's clear_at_least refuses a clearing pass that would not free enough tokens to be worth breaking the cache. Run compaction as a cache-safe fork: same system prompt, same tools, same messages, with the summarization instruction appended last, so the only new input is the instruction. Use the one-hour lifetime across waits longer than five minutes.

Wins: this is what makes 1.3 affordable: with a breakpoint at the end of the system prompt, a compaction writes only the summary and the system prompt stays a cache read (Claude docs); layering lets many sessions share the top. Costs: each compaction or clear is still a rewrite of everything after its seam, and the bar for paying it rises with the price gap (SelfCompact found compaction pays only when the trajectory is more than ten times its summary; cheaper reads make keeping the trajectory cheaper, so on the 0.05x models that bar rises, my extrapolation rather than a measured number); query-aware compression rewrites the prefix on every call and never gets a read (Song, July 2026: 40.1% more expensive than doing nothing on tau-bench retail); Anthropic allows four breakpoints and looks back 20 blocks from each.

Done right: Claude Code's compaction call reuses the parent's exact system prompt, tools and messages and appends one instruction, so a long conversation is read from cache at the very moment it gets summarized. A separate summarizer with its own system prompt would diverge at the first token and pay for the whole conversation fresh.

Agent-aware serving Emerging

When you run the model yourself (vLLM, SGLang, LMCache), the cache is yours, and 2026 research is moving past "exact prefix, evict the least recent." CacheScout (July 2026) learns an agent workflow's transitions online and uses them to decide what to keep and what to prefetch before the next agent call: hit rate up 10 to 18 points, time to first token down 18 to 45%. ReCache (August 2026) computes tool and skill schemas as blocks that can be reused in any order and combination, the thing prefix caching cannot do: 3.655x faster first token at matching tool-invocation accuracy (82.3 vs 82.4 F1). The delta: reuse no longer depends on byte-identical order.

Wins: breaks the prefix rule, so dynamic tool sets and retrieved content stop being cache poison; eviction follows the workflow instead of recency, which matters when a reusable system prompt gets evicted during a long tool call. Costs: only if you own the GPUs; blocks computed without their real neighbors are an approximation of attention whose quality cost has to be tested per workload; research-grade, and none of the hosted APIs in this lesson expose it.

Done right: a platform team serving an open-weight model to a multi-agent workflow where the same few dozen tool schemas recur in different combinations across thousands of calls a minute. That shape is exactly what prefix caching wastes and what composition-invariant blocks recover.

These nest rather than compete. Card two is the floor. Card three keeps you on the floor when the agent's state changes. Card four is where you pay deliberately for 1.3's compaction and 1.2's clearing. Card five changes the physics, but only if you serve your own model. Card one is what you have if nobody ever looked at the hit rate.

Question 2 is where most agents discover they have a problem: a timestamp, a tool list that varies by phase, a customer record in the system prompt. Question 3 is where most of those problems dissolve, and the reason it is load-bearing is that its answer moved this year. In 2025, "can I say it at the tail?" meant building Manus-grade machinery; in October 2026, it usually means using a field the API already has. Question 4 is a budgeting decision, not a layout one: you are choosing to pay, so pay rarely and at a seam. The not-yet leaf is the honest outcome for anything that changes constantly and cannot be appended: it does not belong in a prefix you share.

5Seen in the wild: Codex

In January 2026 OpenAI's Michael Bolin published how the Codex agent loop builds each request, and it reads like a cache design document. The request is ordered from most stable to least: the model's instructions; the tools (the built-in shell and update_plan, web search, and any MCP tools you configured); a developer message describing sandbox and approval rules; your optional developer instructions; a user message that gathers AGENTS.md files (capped at 32 KiB by default) and skill metadata, which is 1.6's catalog sitting in the prefix where it belongs; an environment-context message with the working directory and shell; and only then the conversation. Every follow-up request is the previous one plus new items at the end.

Read the post for the incidents, because they are the curriculum. A bug in how MCP tools were enumerated put them in a different order between requests and silently broke the prefix. MCP servers can announce that their tool list changed, and honoring that announcement mid-conversation triggers an expensive miss. Changing the model changes the instructions slot, which sits above everything. And when you change sandbox mode or directory, Codex appends a new message rather than editing the original: card three, by hand, months before the APIs offered it.

The most architectural detail is the one about state. Codex deliberately does not use the API's server-side conversation state, so that every request is self-contained and works for zero-data-retention customers. That means the full JSON of the conversation is resent on every call, and the bytes on the wire grow quadratically. What keeps the compute linear is the cache. A stateless agent is affordable only because the provider remembers your prefix for a few minutes. That is the same separation 1.2 taught with Managed Agents (the session is not the window), seen from the bill's side.

Read it through 0.4's rule and something new shows up. Cache discipline is not a capability substitute that the next model eats, and it is not a containment boundary either. It got absorbed by the platform: the append-instead-of-edit move Codex made by hand is now a request item in OpenAI's API (configuration_update, for changing reasoning effort mid-conversation), and Manus's logit masks have an API cousin in allowed_tools. The craft is moving into the API; the principle stays in your head, because the API cannot decide for you what belongs at the top.

Claude Code, as a one-line aside: same discipline run as an operational metric, with cache-hit-rate alerts that open incidents, plan mode built as a tool so entering it never changes the tool list, and model switches done only through subagents with their own caches (Shihipar, April 2026).

The misconception

"Fewer tokens means a cheaper agent." It is the most natural belief in context engineering and, on a cached API, often false. Weinberger and Hozez analyzed 2,848 provider-billed coding-agent runs across 103 tasks in July 2026: a compression layer that cut tool-output tokens by 38.4% raised the bill by 6.8%, and across tasks the correlation between token reduction and cost change was 0.15. Cache writes and reads made up about 87% of the reconstructed cost. Compressing a tool result changes it, a changed result breaks the prefix, and the rewrite costs more than the tokens saved. Song (July 2026) found the same for query-aware prompt compression: different compressed text per query means no reads, 40.1% more expensive than not compressing at all. The bill is set by where change lands, not by how many tokens there are.

Hold the opposite error in the other hand: "so never compress." Cached tokens are cheap in dollars and still expensive in attention. A 400k-token window that reads at 0.05x still rots (1.1), still loses the goal (1.5), and still needs 1.3's compaction. The answer is not less compaction; it is compaction placed at a seam, run as a fork of the same prefix, and done rarely enough to clear its own bar.

6Check yourself

A support agent's harness puts "Current time: 14:32:07 · Customer tier: Gold · Open tickets: 3" at the top of the system prompt each turn, and the product lead now wants a different tool set per customer tier. The cache hit rate is near zero. What do you change, and what do you keep?

Move the volatile header out of the prefix and into a reminder appended to the user turn (card three); that alone restores card two. Do not build per-tier tool lists: keep one stable tool set and restrict per tier with allowed_tools, masking, or deferred loading, so the tool definitions never change. If per-customer facts must sit high, layer them the way Claude Code does: global system and tools first, then a per-session block behind its own breakpoint (card four), so a new customer re-pays only their block. Keep the tier logic; move where it is said.

Your coding agent compacts at 150k tokens by calling a separate summarizer with its own short system prompt and no tools. Finance says compaction is now the largest line on the bill. Why, and what is the fix?

The summarizer's request diverges from the cached conversation at its first token, so 150k tokens are paid fresh (or written at 1.25x) on every compaction. Make compaction a cache-safe fork: same system prompt, same tools, same messages, with the summarization instruction appended as the last user message, so the only new input is the instruction. Then add a breakpoint at the end of the system prompt so the post-compaction call writes only the summary. And check whether you are compacting for the right reason: compaction is an attention move (1.3), and with reads at 0.05x it has to compress harder to also be a money move.

A teammate wants to save money by switching a 150k-token Opus 5.5 conversation to Haiku 5.5 for a run of routine steps, then switching back. What do you check before saying yes?

Run the numbers, because "never switch models" is a price ratio, not a law. Staying on Opus reads 150k at $0.20 per million: about $0.03 a step. Switching writes 150k into Haiku's cache at the over-100k rate ($0.625 per million): about $0.09 once, then about $0.0075 a step, so it pays back after roughly three Haiku steps. The trap is the return trip: if more than five minutes pass, the Opus entry expires and coming back re-writes 150k at $5 per million, about $0.75. The cleaner design is Claude Code's: hand the routine work to a Haiku subagent with a few-thousand-token brief (fractions of a cent), and never move the Opus prefix at all.

Done when

Module 1's bar: given any agent misbehavior, your first three hypotheses are context hypotheses, and they are usually right. 1.7 supplies the answers for "it's slow and expensive": (1) something above the tail changes every call (a timestamp, tool order, a mode switch that edits the prompt); (2) the harness edits the middle too often or the wrong way (frequent clears, compaction through a separate prompt, per-query compression); (3) the cache expires or is abandoned (waits past the lifetime, model switches in place). 1.1 supplies "it degraded as the window grew," 1.3 and 1.5 supply "it forgot the goal," and 1.4 and 1.6 supply "it got confused about what to use."
